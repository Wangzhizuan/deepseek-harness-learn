覆盖与未验证判断 ​

这页解决什么问题 ​

本站是非官方的中文源码学习材料，不是 DeepSeek Harness 的官方文档。docs/architecture.md:5 那句 "Read this before changing anything" 指的是官方文档，不是本站；AGENTS.md:7 明确本仓库 "no compatibility promise"（不承诺兼容），所以任何写死的行号、常量、包数都可能在下一个 commit 失效。【设计记录】

这页交代四件事，全部按"宁可承认没读，也不假装读过"的原则写：

  1. 本站实际引用过哪些文件（有 frontmatter 锚点的才算）；
  2. 哪些分组完全没读，以及这在覆盖率上意味着什么；
  3. 全站所有【未验证判断】的逐条清单（13 条）；
  4. 页面过期了你怎么知道。

页面什么时候算过期 ​

三层机制，从强到弱。

第一层：锚点校验（自动，最可靠） ​

learn/scripts/check-anchors.ts:191 的 checkAnchor 逐条打开锚点声明的文件、跳到 line 行、检查是否 includes 那段 expect。找不到就在上下各 DRIFT_WINDOW = 5 行内再找（:37、:229）：

  • 窗口内找到 → 漂移，警告不报错（内容还在，只是行号变了）；
  • 窗口内找不到 → 失效，:294 的 totals.stale > 0 让脚本 exit 1。

结果由 :276 附近的 writeFileSync 写入 learn/.vitepress/anchor-status.json。【源码事实】

第二层：commit 标记（自动，但只是提示） ​

learn/.vitepress/config.ts:68 的 interface LearnMeta 里带构建时 commit，:110 的 readAnchorStatus 把校验结果读进页面数据，learn/.vitepress/theme/PageMeta.vue:84 的 const stale 和 :125 的 stale.length > 0 决定底部要不要弹红框。PageMeta.vue:191 那句"本站是非官方的中文源码学习材料"永远显示。【源码事实】

判断方式：把页面底部的 commit 和你当前的 HEAD 做 git diff --stat <commit>..HEAD -- <本页引用的目录>，有改动就该怀疑。

第三层：本页手写的统计数字（无自动保护） ​

包数、目录数、测试文件数、覆盖比例——这些都没有锚点可以钉住，因为它们不是任何一行代码。它们只受上面"自己复算"那几条命令保护。这是本站最脆弱的一类内容，也是上表第 13 条【未验证判断】的由来。

已知局限，说清楚 ​

  1. 只比对单行子串，不验证语义。const x = 1 变成 const x = 2，expect: "const x" 照样通过。
  2. 不验证跨文件关系。【跨源码分析】的结论里，各个锚点单独都还在，但它们之间的关系可能已经变了，脚本查不出来。
  3. 不检查正文。只校验 frontmatter 声明的锚点；正文里提到但没登记的位置无人看守。
  4. 不在构建时重跑。config.ts:110 读的是上一次的 JSON。改了代码没重跑 learn:check，底部状态就是滞后的。
  5. 死链不拦。learn/.vitepress/config.ts:287 是 ignoreDeadLinks: true。【源码事实】真正的质量门是 check-anchors 和 check-mermaid。

过期不等于没用 ​

一条锚点失效只说明"这一条引用要复核"，不说明整页都错。本站的价值主要在结构（219 个包怎么分组、按什么顺序读、术语怎么对应），结构比行号稳定得多。行号错了，你顺着文件名和 expect 里的标识符 grep 一下就能找回来。

三条原则，也是本站的自我约束：

  1. 诚实优先 —— 没读过就写没读过，本页 34 个"完全没读"的目录就是这条原则的产物。
  2. 锚点先行 —— 每条关键结论都要能被脚本查。查不动的（比如统计数字）明确降级成【未验证判断】。
  3. 以源码为准 —— 本站和源码冲突时，源码对，本站错。
