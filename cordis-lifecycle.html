Cordis 与插件生命周期 ​

这页解决什么问题 ​

DeepSeek Harness 里几乎没有"框架代码调用业务代码"的传统结构。启动时真正发生的事情是：一棵配置树被翻译成一串插件挂载，每个插件声明"我需要哪些服务"和"我提供哪个服务"，然后由 Cordis 决定谁先活、谁后活、谁被卸掉。你在 packages/ 下看到的几百个包，绝大多数都是这个形状。

所以在读任何一个具体包之前，需要先能准确回答四个问题：

  1. Context、Fiber、Service、effect 这四个词分别指什么，它们不是同一层的东西吗？
  2. 一个插件从"被 ctx.plugin() 调用"到"真的跑起来"，中间到底经过了哪些步骤？
  3. 为什么改一个配置、或者换掉一个底层服务实现，上层插件会自动重装？判据是什么？
  4. emit / parallel / serial / bail / waterfall 这五个词，什么时候该用哪个？

范围：本页只讲 vendored Cordis（vendor/cordis/src/）本身的机制，加上 packages/boot/app-boot 里最短的一段真实调用。不讲：Agent 一个回合的调度（见 一个回合发生了什么）、会话日志（见 Session log）、某个具体能力怎么换实现（见 能力接缝）。

先用人话解释 ​

把四个词一次说清：

  • Context 是一份"能力目录"，也是发事件的入口。ctx.tools、ctx.llm、ctx.shell 这些属性不是普通字段，是从目录里查出来的。Context 本体在 vendor/cordis/src/context.ts:42，而 new Context() 返回的其实是一个 Proxy，所有属性读写都要过 ReflectService.handler（context.ts:71–:83）。【源码事实】
  • Fiber 是"这一次挂载"的实例。同一个插件被挂三次，就有三个 Fiber，各自有自己的 config、自己的依赖状态、自己的一堆待清理项。类定义在 vendor/cordis/src/fiber.ts:184。【源码事实】
  • Service 是"占住某个 ctx.<key> 的东西"。Service 的构造函数最后一行就是去注册自己：vendor/cordis/src/service.ts:57 的 self.ctx.reflect.provide(name, self, this[symbols.check])。所以"写一个服务"和"注册一个服务"在 Cordis 里是同一个动作。【源码事实】
  • effect 是"带撤销方式的登记"。你不是"做了一件事"，而是"登记了一件事并同时交出怎么撤销"。ctx.on()、ctx.provide()、甚至 ctx.plugin() 自己，都是 effect：events.ts:256、reflect.ts:278、fiber.ts:265 三处都是 fiber.effect(...)。【源码事实】

一句话串起来：Context 是查询和广播的门面，Fiber 是所有权和生命周期的单位，Service 是被查询的目标，effect 是让"卸载"这件事变得可能的记账方式。

设计文档把最后一条写成了明确规则：docs/cordis-primer.md:13 的 "Registrations are reversible effects"，以及 :44 的 "Every registration should have a disposer"。【设计记录】

智能工厂比喻 ​

想象一座正在改造中的工厂车间。

  • Context = 车间墙上的接口墙。 墙上有一排标好名字的接口位：shell、llm、tools、sessions。谁想用压缩空气，不去找具体哪台压缩机，而是去墙上找 air 这个接口位。
  • Service = 插在接口位上的设备。 一个接口位同一时刻只能插一台设备。第二台设备想插同一个位，安装工会当场拒绝——reflect.ts:290 抛的就是 service "<name>" has been registered at <...>。【源码事实】
  • Fiber = 一张设备安装工单。 工单上写着：装什么、配置参数是什么、开工前必须哪些上游设备已经在线（inject）、以及一份施工登记本（_disposables）。
  • effect = 施工登记本上的一行。 每一行不只写"我拉了一根管子"，还写"拆的时候先关阀再断管"。这就是为什么这座工厂可以随时把某台设备连带它拉过的所有管线一起拆干净。
  • 子插件 = 由这张工单派生的下级工单。 关键是：下级工单本身就是上级登记本上的一行。fiber.ts:265 的 this.dispose = parent.fiber.effect(() => { ... }, 'ctx.plugin()') 就是这句比喻的字面实现。撤掉上级工单，下级工单会作为一条登记项被一并撤销。【源码事实】
  • epoch = 上游设备的铭牌编号串。 开工前，安装工把每个必需上游设备的铭牌号抄下来拼成一串（fiber.ts:611 的 epoch += ':' + impl.fiber.uid）。只要这串变了——哪怕换上去的是同型号新机——就按"上游变了"处理。【源码事实】
  • 五种派发模式 = 车间广播的五种喊法。 详见下面的对照表。

比喻的限制 ​

比喻在四个地方会骗人，必须当场纠正。

限制一：拆除不是"倒序一件件拆"，而是"反序取出、并发等待"。 两层需要分开看。单条 effect 内部确实是严格反序串行：fiber.ts:431 的 for (const disposable of disposables.splice(0).reverse())，并且如果某一步返回 Promise，后续会用 task.then(...) 串起来。但整个 fiber 卸载是另一回事：fiber.ts:676 是 await Promise.all(this._disposables.clear().map(async (dispose) => { ... }))。DisposableList.clear() 在 utils.ts:30 确实 return values.reverse()，所以清理任务是按反序发起的，但 Promise.all 意味着它们并发进行、没有"上一个 disposer 完全结束后才开始下一个"的保证。【源码事实】所以"如果 teardown 顺序重要，就把相关工作放进同一个 effect"这条设计建议（docs/cordis-primer.md:44 所在段落）不是风格偏好，而是唯一能拿到顺序保证的写法。【设计记录】

限制二：接口墙不是全局唯一的一面墙。context.ts:121 的 isolate(name, label?) 会在子树里给某个服务名换一个 symbol 作用域，于是同名服务在父树和子树各有一份实现，互不覆盖。context.ts:141 的 intercept() 同理，它让子树里的插件看到不同的服务配置。比喻里"一面墙、一个接口位"的直觉在这里失效。【源码事实】

限制三：每个插件拿到的不是"那个 Context"，而是一个新的派生 Context。fiber.ts:236 是 this.ctx = this.context = parent.extend({ fiber: this })，而 context.ts:99 的 extend() 用 Object.create(...) 走原型链继承。所以 ctx 在不同插件里是不同对象，只是继承链指向同一个根。这也是"ctx.effect() 到底记在谁账上"能有确定答案的原因：记在 ctx.fiber 上。【源码事实】

限制四：waterfall 不是"喊一声"，是"套一层"。 比喻里的广播都是"发出去"。但 events.ts:234 的 waterfall 把最后一个参数 pop() 出来当作最内层的 next，然后让监听器从外到内层层包裹；不调 next() 就把后面所有监听器连同框架自带的默认行为一起否决。docs/cordis-primer.md:28 明确称之为 around-middleware。【源码事实】【设计记录】它更像"审批链上每一环都能改单据、也能直接压下不批"。

真实概念和结构图 ​

第一张图是四个概念的所有权关系。

图说明：注意 F1 有两个上游箭头，这不是画错。registry.ts:330 负责创建它（new Fiber(this.ctx, config, Inject.resolve(plugin.inject), runtime, getOuterStack)），而 fiber.ts:265 负责让父 fiber 拥有它。创建和拥有是两件事，这是理解"为什么卸载父插件会连带卸载子插件"的关键。【源码事实】

第二张图是 Fiber 的状态机。六个状态定义在 fiber.ts:147：PENDING、LOADING、ACTIVE、FAILED、DISPOSED、UNLOADING。

图说明：这张图有两个反直觉之处，都能在源码里定位。

第一，状态不是"设"出来的，是"算"出来的。fiber.ts:574 的 _getState() 按固定优先级推导：uid === null → DISPOSED；有 _error → FAILED；epoch !== INACTIVE → ACTIVE；否则 PENDING。只有 LOADING 和 UNLOADING 是转换过程中显式返回的。【源码事实】

第二，UNLOADING 之后不一定就结束了。fiber.ts:675 的 _unload() 在清理完成后会重新看一眼 epoch：如果 epoch 已经不是 INACTIVE，它会立刻 this.inertia = this._reload() 并回到 LOADING。反过来 _reload()（fiber.ts:646）在结束时也会检查 epoch 是否被中途改掉，若被改掉就转去 _unload()。这两个方法互相尾调用，构成了 HMR 与依赖变更下的重装循环。【源码事实】

一条真实调用路径 ​

下面这条链路取自真实启动流程：boot() 挂载 Loader，Loader 注册成服务，等着它的插件因此被激活。18 跳。

  1. packages/boot/app-boot/src/index.ts:764 —— const ctx = new Context()。整个进程的服务目录在这里诞生。【源码事实】
  2. vendor/cordis/src/context.ts:71 —— 构造函数先建 Proxy，再 this.fiber = new Fiber(self, {}, Object.create(null), null, () => [])（:77）。第四个参数 runtime 传 null，走的是 fiber.ts:321 那个分支：uid = 0、state = FiberState.ACTIVE、dispose = () => this.restart()。根 Fiber 从不 PENDING，也不真正消失，"卸载根 fiber"等于重启它。【源码事实】
  3. packages/boot/app-boot/src/index.ts:770 —— ctx.provide('dshHomePath', dshHomePath)。启动第一个动作是往目录里放一个纯数据服务。【源码事实】
  4. vendor/cordis/src/reflect.ts:278 —— provide() 立刻把注册包成 this.ctx.fiber.effect(...)，标签是 ctx.provide("dshHomePath")。注册即登记，撤销路径同时就位。【源码事实】
  5. packages/boot/app-boot/src/index.ts:771 —— await ctx.plugin(Loader)。注意有 await：registry.plugin() 返回的对象被塞了 then，await 它等价于 fiber.await()。【源码事实】
  6. vendor/cordis/src/registry.ts:316 —— plugin() 先 resolve(plugin) 判形态（函数 / 有 apply 的对象），不合法就抛 invalid plugin, ...；然后 this.ctx.fiber.assertActive()——在已卸载的 context 上挂插件是错误，不是静默忽略。【源码事实】
  7. vendor/cordis/src/registry.ts:330 —— new Fiber(this.ctx, config, Inject.resolve(plugin.inject), runtime, getOuterStack)。runtime 是按 callback 缓存的共享记录，同一插件多次挂载共用一个 runtime、各自一个 Fiber。【源码事实】
  8. vendor/cordis/src/fiber.ts:236 —— this.ctx = this.context = parent.extend({ fiber: this })。插件从此拿到自己的 ctx，ctx.fiber 指向本次挂载。【源码事实】
  9. vendor/cordis/src/fiber.ts:265 —— this.dispose = parent.fiber.effect(() => { ... }, 'ctx.plugin()')。子 fiber 成为父 fiber 登记本上的一行；它的 cleanup 里会 this.uid = null、发 internal/plugin、从 registry 摘掉，并等 inertia 排空。【源码事实】
  10. vendor/cordis/src/fiber.ts:302 —— this.context.emit('internal/plugin', this)。此刻 fiber 还是 PENDING，注释明说要保留这个"历史 PENDING 视图"，因为 loader 可能在这个通知里追加 inject。【源码事实】
  11. vendor/cordis/src/fiber.ts:318 —— 发布之后才 this._refresh()，且前置条件是 this.uid !== null && parent.fiber.state !== FiberState.UNLOADING（:314）。【源码事实】
  12. vendor/cordis/src/fiber.ts:611 —— _refresh() 遍历 inject 的每个名字，缺一个就把 epoch 设成 INACTIVE，否则拼出 ':<uid>:<uid>...'。【源码事实】
  13. vendor/cordis/src/fiber.ts:625 —— _setEpoch()：epoch 没变直接 return；INACTIVE → 有值 则 this.inertia = this._reload() 并置 LOADING。【源码事实】
  14. vendor/cordis/src/fiber.ts:646 —— _reload() 先 await Promise.resolve() 让出一拍。注释解释得很直白：在这个检查点之前入队的 disposer 可能已经让这次加载作废，不能为一个过期的 epoch 执行插件代码。【源码事实】
  15. vendor/cordis/src/fiber.ts:641 —— _resolveConfig() 先跑 internal/config 这个 waterfall，再交给 resolveConfig(runtime, config) 做 schema 校验。配置校验失败会变成 FAILED，由 await() 抛出。【源码事实】
  16. vendor/cordis/src/fiber.ts:356 —— _execute() 调 runtime.callback。如果插件是 class（isConstructor 为真），这里 new 出实例并跑 initHooks；返回值必须是 disposer、Promise、iterable 或 null，否则抛 Invalid effect。【源码事实】
  17. vendor/cordis/src/service.ts:57 —— Loader 作为 Service 子类，构造函数末尾 self.ctx.reflect.provide(name, self, this[symbols.check])，ctx.loader 就位；若该名字已被占用，reflect.ts:290 在这里抛错。【源码事实】
  18. vendor/cordis/src/reflect.ts:314 —— notify(['loader']) 遍历 registry 里所有 fiber，凡 inject 含 loader 且隔离作用域匹配的，都 _checkImpl() + _refresh()；它们的 epoch 因此从 INACTIVE 变为有值，回到第 13 步开始激活。最后 packages/boot/app-boot/src/index.ts:771 的 await 落到 fiber.ts:704 的 await()，把 inertia 排空并把启动错误抛出来。【源码事实】

这条链路的核心结论：没有任何一处代码"决定加载顺序"。顺序完全是 provide → notify → _checkImpl → _refresh → _setEpoch 这条反应链的涌现结果。【跨源码分析】

常见误解 ​

误解一："ctx 是全局单例。" 不是。fiber.ts:236 让每个 fiber 拿到 parent.extend({ fiber: this }) 的新对象。它们通过原型链共享根上的服务，但 ctx.fiber、ctx[Context.intercept]、ctx[Context.isolate] 都可能不同。判断"这个 effect 记在谁账上"永远看 ctx.fiber。【源码事实】

误解二："fiber 卸载时 disposer 严格倒序、一个接一个执行。" 只在单条 effect 内部成立（fiber.ts:431）。fiber 整体卸载是 Promise.all 并发（fiber.ts:676），只保证发起顺序是反序（utils.ts:30）。需要严格顺序，就把相关清理写进同一个 effect。【源码事实】

误解三："依赖只要还在，插件就不会重装。" 判据不是"服务名还在"，而是 epoch 字符串。fiber.ts:611 把 impl.fiber.uid 拼进 epoch，所以换一个提供者、同名服务重新注册都会改变 epoch，进而触发一次完整的卸载—重装。反之，fiber.ts:625 开头的 if (epoch === oldEpoch) return 保证重复通知不会造成多余重装。【源码事实】

误解四："waterfall 就是能改参数的 emit。" 差别在否决权。events.ts:234 里 next 是被 pop() 出来的最内层回调，框架自带行为也在这条链的最里面。监听器不调 next()，默认行为就不会发生——fiber.ts:736 的 internal/update 正是靠这个让 HMR 能拦下一次重启。emit 没有这个能力。【源码事实】

误解五："插件加载失败会让启动崩掉。"_reload() 的 catch（fiber.ts:661）把错误交给 ctx.logger.error 并记进 _error，fiber 变 FAILED，不会向上冒泡。错误只在有人 await fiber.await() 时被重新抛出（fiber.ts:704）。packages/boot/app-boot/src/index.ts:771 之所以写 await，就是为了让 Loader 的失败真的变成启动失败。【源码事实】

误解六："FiberState.UNLOADING 是终态。" 终态只有 DISPOSED。_unload() 结束时若发现 epoch 已恢复，会直接接上 _reload() 回到 LOADING（fiber.ts:688 的 _updateState 回调里，:692 直接接上 this.inertia = this._reload()）。【源码事实】

三道自测题 ​

第一题：某插件 inject = ['shell']。运行中，提供 shell 的插件被卸载后又用完全相同的配置重新挂载。这个插件会经历几次状态变化？为什么不能"因为服务名没变所以什么都不做"？

参考答案

会经历完整的 ACTIVE → UNLOADING → PENDING → LOADING → ACTIVE。原因是 epoch 由 impl.fiber.uid 组成（fiber.ts:611），新挂载的提供者是一个新 Fiber、新 uid，epoch 字符串必然不同。第一次 notify（reflect.ts:314）发生在旧服务摘除时，_checkImpl 找不到实现 → epoch 变 INACTIVE → 卸载；第二次 notify 发生在新服务注册时 → epoch 变成新串 → 重装。fiber.ts:625 的 if (epoch === oldEpoch) return 只能挡住"epoch 完全没变"的重复通知，挡不住这种情况。【源码事实】

第二题：你写了一个插件，它先 ctx.provide('a', ...)，再 ctx.on('some-event', ...)，再 ctx.plugin(Child)。卸载这个插件时，这三件事的清理顺序有保证吗？

参考答案

没有严格的串行顺序保证。 三者都是同一个 fiber 上的三条独立 effect（分别来自 reflect.ts:278、events.ts:256、fiber.ts:265），fiber 卸载走 fiber.ts:676 的 Promise.all，只保证"按反序发起"，不保证"前一条完全结束再开始下一条"。如果 Child 的清理必须发生在 a 摘除之前，唯一可靠的写法是把它们收进同一个 ctx.effect()，让 fiber.ts:431 的反序串行生效。这正是 docs/cordis-primer.md:44 那段设计建议的技术依据。【源码事实】【设计记录】

第三题：为什么在 disposer 里调用 ctx.effect() 会抛错，而在 internal/plugin 监听器里对一个还是 PENDING 的 fiber 调 ctx.effect() 却合法？

参考答案

因为门禁检查的是两个不同条件。fiber.ts:419 先 assertActive()（只看 uid !== null），:420 再拒绝 state === FiberState.UNLOADING。disposer 运行时 fiber 正处于 UNLOADING，命中第二条 → 抛 INACTIVE_EFFECT，由 cordis-lifecycle.spec.ts:98 固定。PENDING 既不是 UNLOADING、uid 也不为 null，所以两条都不命中，登记合法；这些 pre-activation 的 effect 会在后续 _unload() 时被清掉，由 cordis-lifecycle.spec.ts:117 固定。【源码事实】【测试行为】
