仓库地图 ​

这页解决什么问题 ​

219 个 package 记不住，也没必要记住。这页把它们压成 12 个分组，每组给一句职责、一个代表 package、一条"什么情况下你要来这儿"。

同时解决三个新读者最容易卡住的问题：入口在哪（dsh 命令怎么变成一棵插件树）、vendor 和 packages 的界线在哪（哪些是上游框架、哪些是本仓库代码）、测试怎么当文档用（216 个 tests/ 目录里有 640 个 spec）。

如果你还没读过 /harness-explained，先读那页——本页假设你已经知道 plugin、Context、seam、session log 这几个词大概指什么。

先记住三条命名规律，比记 219 个名字有用 ​

AGENTS.md:13 定义了目录约定：包都在 packages/<group>/<pkg>/，包名是 @deepseek-ai/dsh-<pkg>；AGENTS.md:57 把分组说明指向 packages/README.md。【设计记录】在这个约定之上，实际命名有很强的规律性，认出规律就等于认出角色。

规律一：和分组同名的那个包，就是这个能力的接口（Service Definition，服务定义）。

实测有 25 个分组存在同名包：shell/shell、fs/fs、llm/llm、web/web、subagent/subagent、sandbox/sandbox、terminal/terminal、subprocess/subprocess、storage/storage、skill/skill、spill/spill、jobs/jobs、goal/goal、lsp/lsp、workflow/workflow、compaction/compaction、attachment/attachment、credentials/credentials、settings/settings、session-query/session-query、code-runtime/code-runtime、workspace/workspace、schedule/schedule、e2b/e2b、acp/acp。【跨源码分析】

想知道某个能力的接口长什么样，闭着眼睛去 packages/<x>/<x>/src/index.ts 就对了。以 shell 为例，packages/shell/shell/src/index.ts:40 就是 declare module '@deepseek-ai/cordis'，块里声明 interface Context { shell: ShellExecutor }——接口通过模块声明合并（module augmentation）把 ctx.shell 挂到 Context 类型上。【源码事实】

规律二：带后缀的是实现（Provider），tool- 前缀的是模型可见的工具（Consumer）。

命名形状角色实测数量例子
<cap>/<cap>Service Definition25shell/shell、fs/fs
<cap>-<impl>Service Provider数十个bash-local、bash-sandbox、fs-local、llm-deepseek、storage-sqlite
*-policy策略插件（挂在接缝事件上）5fs-observation-policy、sandbox-policy、spill-policy、guard/timeout-policy、session-checkpoint-policy
tool-<x>Consumer，模型可见的工具21tool-bash、tool-fs、tool-web、tool-subagent
ui-<x>前端插件32ui-conversation、ui-settings、ui-trajectory
command-<x>人类命令（不经过模型回合）3command-compact、command-goal、command-feedback

【跨源码分析】

21 + 32 + 3 = 56 个包，占 219 的四分之一强，全部按这三种形状命名。它们几乎不需要单独学——认出形状就知道它在接缝三角里坐哪个位置。这也解释了"为什么 219 个包不算过度工程"：AGENTS.md:109 规定一个能力接缝必须由 Service Definition / Service Provider / Consumer 三个角色齐全组成，"单独一个角色不叫接缝"，于是能力数量自动乘以三。【设计记录】

规律三：packages/shell 是标准样板。 AGENTS.md:111 明确写 dsh-shell 的 request/spec 拆分"is the template"（是这类设计的模板）。【设计记录】读不懂某个接缝时，去 shell 组对照同名文件，通常五分钟解决。

12 个分组 ​

图说明：① vendor 是上游 Cordis 框架（9 个 workspace 成员，不计入 219）；② core 是产品主干，所有其他分组都围着它。③ 装配与启动组负责把插件树组装出来，同时装配前端。围绕 core 有四类能力接缝（④执行环境 ⑤文件与代码 ⑥模型 ⑦外部世界，共 54 个包）伸向外部世界；⑧ 会话数据组负责把事实落盘；⑨ 编排与委派、⑩ 人机交互与治理挂在 core 的事件上；⑪ 前端与宿主是最大的一组（47 个包）；⑫ 协议与开发支撑在旁边支撑全部。

完整版（节点较多，按原尺寸渲染，可左右拖动查看）

完整版图说明：这张图把 12 个分组展开成主要的一级目录，并标出各自的包数量。vendor/cordis 在最上游；core（8 个包）居中；启动侧是 boot（2）← bundle（3）← examples（3）与 preset（2）。core 向下辐射出各能力接缝目录：执行环境侧的 shell（9）、subprocess（2）、terminal（3）、sandbox（4）；文件代码侧的 fs（7）、lsp（3）；模型侧的 llm（5）；外部世界侧的 web（6）、skill（4）。数据侧是 session（13）与它派生的 session-query（4）、以及 compaction（4）。编排侧是 subagent（11）、workflow（4）、goal（4）。交互侧是 interaction（5）。前端侧是 client（39）与 host（8）。支撑侧是 test-support（6）与 util（7）。图中未画出的分组（storage、spill、attachment、context、guard、hooks、settings、credentials、api、sdk、typert、extensions、identity、acp、mcp、plan、todo、schedule、workspace、code-runtime、e2b、feedback、runtime-diagnostics）职责见下方表格。

下面是完整的 12 组，49 个一级目录一个不漏，包数合计 219。【跨源码分析】

① 上游框架 —— vendor/（9 个 workspace 成员，不计入 219） ​

cordis、cosmokit、group、hmr、include、loader、logger-console、schemastery、timer。

这是 vendored（内联）进来的 Cordis 生态。它们是 pnpm workspace 成员（pnpm-workspace.yaml:2 的 - vendor/*），和 packages/*/*（:3）一起构建，同步流程记在 vendor/README.md。【源码事实】

边界怎么划：vendor/ 是通用插件框架，完全不知道"Agent"、"模型"、"工具"这些概念——vendor/cordis/src 只有 9 个文件（context.ts、events.ts、fiber.ts、index.ts、logger.ts、reflect.ts、registry.ts、service.ts、utils.ts），里面没有任何 Agent 词汇。packages/ 是产品，它把 Agent 的一切表达成 Cordis 插件。判断一段代码属于哪边，问一句"这段逻辑换成做一个聊天机器人还成立吗"——成立就是 vendor 该管的。【跨源码分析】

什么情况来这儿：搞不懂插件卸载为什么干净、服务冲突为什么报错、事件为什么必须调 next()。核心两个文件：vendor/cordis/src/context.ts:42（export class Context {，全文件仅 146 行）和 vendor/cordis/src/fiber.ts:184（export class Fiber {，全文件 754 行）。详见 /cordis-lifecycle。

② 产品主干 —— core/（8 个包） ​

agent、agent-loop、agent-default-model、agent-tool-presentation、scope、session、system-prompt、tools。

docs/architecture.md:43 起的表格给出了它们各自持有的 ctx 键：core/session → ctx.sessions、core/system-prompt → ctx.systemPrompt、core/tools → ctx.tools、core/agent → ctx.agents、core/agent-loop → ctx.agentLoop、core/scope 是库没有键。【设计记录】

注意 agent 和 agent-loop 的分工：前者定义 Agent 接口、活跃注册表和 agent/* 事件，后者是实现那个接口的默认驱动。回合边界事件都在 packages/core/agent-loop/src/agent.ts（496 行），例如 :255 的 turn/start；产品与模型的唯一接触面在同文件 :345 的 llm.stream(request)。【源码事实】

什么情况来这儿：几乎所有"这个行为到底谁决定的"问题最终都指向这 8 个包。这一组是全仓库唯一必须完整理解的分组。

③ 装配与启动 —— boot/(2) + bundle/(3) + preset/(2) + examples/(3) = 10 个包 ​

boot/app-boot、boot/cmdline；bundle/base、bundle/headless、bundle/web-app；preset/agent-presets、preset/persona；examples/ 下 3 个 demo bundle。

层叠规则的权威描述在 docs/architecture.md:27："Layers apply to an empty entry list in this order"——先按 profile 列出的顺序应用每个 bundle，再是 profile 自己的 cordis.patch.yml，再是 home 级的，最后是 --patch 覆盖层。:23 说 profile 和 bundle 都在自己的 package.json 的 dsh 字段里声明自己；:25 指出 dsh-base 是每个 profile 的第一层。【设计记录】

代码验证：packages/bundle/base/package.json:36 就是 "dsh": {，里面是 bundle.patch 指向 ./cordis.patch.yml；类型定义在 packages/boot/app-boot/src/profile.ts:50 的 bundles?: string[]；profile 目录常量在同文件 :36 的 export const PROFILES_DIR = 'profiles'。【源码事实】

什么情况来这儿：想知道"我这台机器上到底挂了哪些插件"。docs/architecture.md:32 给的命令是 dsh --profile web --dump-config，对应代码是 apps/cli/src/dump-config.ts。【设计记录】

④ 执行环境接缝 —— shell/(9) + subprocess/(2) + terminal/(3) + sandbox/(4) + code-runtime/(2) + e2b/(3) = 23 个包 ​

shell 组是最完整的样板，9 个包正好演示了一个接缝能长多大：接口 shell，环境 shell-env，四个 Provider（bash-local、bash-sandbox、pwsh-local、pwsh-sandbox），三个 Consumer（tool-bash、tool-bash-persistent、tool-pwsh）。

docs/architecture.md:102 解释了为什么值得这么分：文件系统和子进程 Provider 共享同一个"执行世界"，把它们指向远程沙箱，Bash、PTY、LSP 一起搬走，不需要 fork 任何 Provider。e2b 组就是这句话的 POC。【设计记录】

什么情况来这儿：加一种新的命令执行方式、让工具在容器/远程里跑、排查"为什么这条命令被拦了"（看 sandbox/sandbox-policy）。

⑤ 文件与代码接缝 —— fs/(7) + lsp/(3) + workspace/(1) = 11 个包 ​

fs 组同样是完整三角：接口 fs，Provider fs-local / fs-sandbox，策略 fs-observation-policy，Consumer tool-fs / tool-fs-search / tool-str-replace-editor。

什么情况来这儿：改文件读写工具的行为、加路径白名单、接语言服务器。

⑥ 模型接缝 —— llm/(5 个包) ​

llm（接口 + 消息/流词表）、llm-deepseek、llm-pi-ai（两个 Provider）、llm-retry、token-meter。

只有 5 个包但重要度极高：docs/architecture.md:110 说加一个模型提供方的方式就是"register its adapter on ctx.llm"。【设计记录】packages/core/agent-loop/src/agent.ts:345 那一行 this.loopCtx.llm.stream(request) 就是产品和模型的全部接触面。【源码事实】

什么情况来这儿：接新模型、改重试策略、算 token。

⑦ 外部世界接缝 —— web/(6) + mcp/(1) + skill/(4) + storage/(4) = 15 个包 ​

web 组是"一个接口多个搜索引擎"的典范：接口 web，Provider web-fetch-http、web-search-deepseek、web-search-exa、web-search-perplexity，Consumer tool-web。mcp/mcp-client 是 MCP 协议客户端。skill 组管技能包的注册与加载。storage 组（storage、storage-domain、storage-json、storage-sqlite）是通用键值/文档存储接缝，注意它和 ⑧ 组的会话持久化不是一回事。

什么情况来这儿：换搜索引擎、接 MCP server、给插件找个存东西的地方。

⑧ 会话数据与上下文经济 —— session/(13) + session-query/(4) + compaction/(4) + spill/(3) + attachment/(2) = 26 个包 ​

这一组回答"日志写下来之后发生了什么"。session 组 13 个包分三簇：持久化（session-persistence 协调器 + session-persistence-sqlite + session-persistence-jsonl + session-checkpoint-policy）、派生（session-projection、session-projection-cache、session-stats）、标题与遥测（4 个 session-title-* + session-telemetry + session-telemetry-otel）。

compaction 与 spill 是"上下文经济"：上下文太长要压缩（compaction-basic、compaction-tool-result-pruner）、太大要溢出到别处（spill-local）。

关键事实：SQLite 的磁盘结构版本在 packages/session/session-persistence-sqlite/src/schema.ts:20，当前 SCHEMA_VERSION = 15。【源码事实】

什么情况来这儿：会话丢了、恢复不对、转录导出不对、上下文爆了。日志本体的语义在 ② 组的 core/session（packages/core/session/src/index.ts:792 的 export class SessionStore extends Service），见 /session-log。

⑨ 编排与委派 —— subagent/(11) + workflow/(4) + goal/(4) + context/(4) + jobs/(3) + guard/(2) + plan/(1) + todo/(1) + schedule/(1) = 31 个包 ​

这是仅次于前端的第二大类，也是最容易被低估的一类。 subagent 组 11 个包展示了"委派"能有多少种形态：接口 subagent，Provider 包括 subagent-acp、subagent-claude-code、subagent-codex、subagent-dsh-sdk、subagent-fork-in-process、subagent-spawn-in-process、subagent-in-process-driver，Consumer 是 tool-subagent、tool-subagent-control、tool-subagent-report。docs/architecture.md:102 说这些 Provider "vary just as widely behind one interface, from a fresh child agent to a delegated turn in another product"。【设计记录】

context 组（agent-instructions、session-reference、time-context、tmux-context）是"往模型上下文里塞东西"的四个正例——你想加一段自动注入的上下文，抄这四个，不要在 agent/pre-step 里直接拼字符串。

guard 组只有 2 个包（repeat-tool-reminder、timeout-policy），但它们是"循环卫生"：防止模型反复调同一个工具、给工具加超时。

什么情况来这儿：加子 Agent、加后台任务、加自动注入的上下文、治理跑飞的循环。

⑩ 人机交互与治理 —— interaction/(5) + hooks/(3) + settings/(2) + credentials/(2) + feedback/(2) + identity/(1) + acp/(1) = 16 个包 ​

interaction 组是 commands、permission-presets、tool-ask-user、user-approval、user-questions——权限审批和"反问用户"都在这儿。hooks 组（hook-protocol、hooks-claude-code、hooks-codex）是外部工具钩子的桥接。credentials 是凭据引用（credentials + credentials-local），注意它管的是引用，不是明文。

什么情况来这儿：改权限弹窗行为、加斜杠命令（docs/architecture.md:115：注册到 ctx.commands，"it dispatches without a model turn"，不走模型回合）、接凭据。【设计记录】

⑪ 前端与宿主 —— client/(39) + host/(8) = 47 个包 ​

这是最大的一组，占 219 的 21.5%，而且对理解架构基本没有帮助。 如果你的目标是"理解 Harness 怎么工作"，这 47 个包可以整体跳过。

client 组：6 个基础设施包（connection、hmr、locale、modules、runtime、schema-form）+ 31 个 ui-* 插件 + web / web-react 两个装配。host 组是浏览器 UI 的宿主侧（webserver、apiproxy、frontend-static、plugin-inventory 和 4 个 directory-picker-*）。

什么情况来这儿：只有你要改浏览器界面的时候。

⑫ 协议与开发支撑 —— util/(7) + test-support/(6) + typert/(4) + extensions/(4) + sdk/(3) + api/(2) + runtime-diagnostics/(1) = 27 个包 ​

util 是零依赖工具（atomic-write、brand、home-paths、launch-environment、native-command、output-retention、timeout）。test-support 是测试基础设施（agent-loop-testkit、llm-mock-server、llm-replay、acp-snapshot、client-runtime、loader-smoke）——写测试前先看这 6 个，别自己造 mock。 typert 是类型图生成器与运行时注册表，api 是远程 BFF 与 Typert RPC 网关，sdk 是 JSON-RPC 协议/服务端/客户端，runtime-diagnostics/invariants 集中放运行时不变量。extensions 组（cordis-client-runner、cordis-host-runner、tool-cordis、ui-cordis）很有意思：它让 Agent 自己检视和挂载自己的插件。

什么情况来这儿：写测试、接 SDK、让 Agent 自省。

入口在哪 ​

从命令到插件树，一共四跳，全部实测：

  1. apps/cli —— 包名 @deepseek-ai/dsh，apps/cli/package.json:15 的 "dsh": "lib/bin.js"（在 bin 字段里）就是 dsh 这个命令的来源。【源码事实】
  2. apps/cli/src/bin.ts —— 53 行的分发器，三种模式：:30 case 'profile': {（正常启动）、:40 case 'plugin': {（插件管理）、:45 case 'dump-config': {（打印实际插件树）。文件顶部注释说明"Dynamic imports per mode keep unrelated modes out of each dispatch path"。【源码事实】
  3. apps/cli/src/profile-boot.ts:207 —— export async function runProfile(...)，返回 { ctx: Context; shutdown: ProcessShutdown }。同文件 :100 调 loadProfile(NAME, name, INSTALL_ANCHOR, ...)，:151 遍历 composeEntries([bundlePatches, profile.patches, homePatches, overlays])——这一行就是 docs/architecture.md:27 那条层叠规则的代码形态，四个数组的顺序和文档里那句话一一对应。【源码事实】
  4. packages/boot/app-boot/src/profile.ts —— profile / bundle 清单的类型与解析。:36 PROFILES_DIR = 'profiles'，:50 bundles?: string[]。【源码事实】

apps/ 下另有 apps/web。pnpm-workspace.yaml:9 的 - apps/* 把它们纳入 workspace，注释写着"apps/cli owns the dsh bin"。本站自己也是 workspace 成员，在 pnpm-workspace.yaml:13 的 - learn。【源码事实】

另外注意 apps/cli/package.json 的依赖列表里直接列了 60 多个 workspace:^ 包——这份依赖清单本身就是一张"CLI 实际会用到哪些包"的地图，比任何文档都新。想知道某个包是否在默认 CLI 里，grep 这个文件最快。【跨源码分析】

怎么用测试当文档 ​

测试目录约定：packages/<group>/<pkg>/tests/。实测有 216 个 tests/ 目录（219 个包里 216 个有测试）、640 个 .spec.ts、44 个 .e2e.ts。相比之下 packages/*/*/src/ 顶层只有 887 个 .ts 文件——测试与源码几乎 1:1.4。【跨源码分析】

三个实用技巧：

技巧一：spec 文件名就是子系统的功能清单。 packages/core/agent-loop/tests/ 里 20 个文件的名字直接告诉你 agent-loop 有哪些关注点：cancel.spec.ts、interception.spec.ts、invariant.spec.ts、resume.spec.ts、scope-lifecycle.spec.ts、tool-order.spec.ts、properties.spec.ts、request-error.spec.ts、request-reconstruction.spec.ts……想知道"取消是怎么处理的"，别读 496 行的 agent.ts，先读 cancel.spec.ts。【跨源码分析】

技巧二：it(...) 的描述就是一句可验证的规格。 例如 packages/core/agent-loop/tests/tool-calls.spec.ts:99 的 describe('tool-call scheduler: grouping and barriers', ...)，下面第一条用例叫 "runs parallel-safe siblings concurrently (all start before any completes)"——一句话说清了并发语义，比读调度器实现快十倍。同文件还有 5 个 describe：:220 乱序结算仍按模型顺序返回、:264 并发池遵守 maxParallelToolCalls、:369 有序中间件与附加上下文、:459 取消处理、:633 失败静默。这 6 个 describe 合起来等于一份调度器规格目录。【测试行为】

技巧三：.e2e.ts 和 properties.spec.ts 是两种特殊读法。 44 个 .e2e.ts 跑的是真链路（如 packages/core/agent-loop/tests/request-cache.e2e.ts），适合看"实际怎么串起来"；properties.spec.ts（agent-loop 和 core/session 都有）是属性测试，里面写着的不变量往往就是这个子系统最硬的约束。【跨源码分析】

一句话总结：读一个陌生包，先 ls 它的 tests/，再读最像你问题的那个 spec，最后才进 src/。

不必读的部分（重要） ​

诚实地说，为了理解架构，下面这些可以整体跳过，合计约占 219 个包的一半：

  • ⑪ 前端与宿主 47 个包（21.5%）——除非你改界面。
  • 32 个 ui-* 包（已含在上面）——它们是"一个界面功能一个插件"的机械展开。
  • 21 个 tool-* 包——读两个就够了（建议 shell/tool-bash 和 fs/tool-fs），剩下 19 个结构同构。【未验证判断】这是抽样阅读后的印象，没有逐个核对 21 个包。
  • 大部分 Provider 变体——llm-pi-ai、pwsh-sandbox、web-search-perplexity、subagent-codex 这类，每个接缝读一个 Provider 即可。
  • examples/（3 个）与 e2b/（3 个） —— demo 与 POC，不代表主线设计。
