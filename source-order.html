源码阅读顺序 ​

这页解决什么问题 ​

219 个 package，你不可能按字母序读。这页给两样东西：

  1. 一条固定的前 10 个 package 顺序——不管你的目标是什么，都建议按这个顺序过一遍，约半天。
  2. 六条按目标裁剪的路径——知道自己要干什么之后，只读那条路上的包。

前置：读过 /harness-explained 和 /repo-map。本页只管顺序和"为什么这个顺序"，不解释子系统内部，那是四篇核心页的事。

为什么必须有顺序：三条依赖链 ​

先看清楚三条不可逆的依赖方向，顺序就是从它们推出来的。

图说明：A → B → C 是硬依赖，跳读一定卡住：不懂 Context/Fiber 就看不懂插件为什么这么写；不懂 profile/bundle 就不知道哪些插件在跑。C → D 和 C → E 是软依赖，可以按目标只选一支。所以正确策略是"A B C 三段都读，D E 两支按需选"。

前 10 个 package：固定顺序（约半天） ​

选择标准三条：①在依赖链上不可跳过；②读完能解释一类"为什么"；③有配套 spec 可以立刻验证。

合计约 6.5 小时。下面逐个说"为什么在这个位置"和"具体看哪几行"。

1. vendor/cordis —— 先学机制，不学产品 ​

docs/architecture.md:11 把 Cordis 定为整个 Harness 的运行时基础。【设计记录】AGENTS.md:3 那句 "everything is a plugin" 只有在你读过 Cordis 之后才不是口号。【设计记录】

只看两个类：vendor/cordis/src/context.ts:42 的 export class Context {（整个文件仅 146 行，很薄，Context 主要是个门面）和 vendor/cordis/src/fiber.ts:184 的 export class Fiber {（754 行，真正的生命周期在这儿）。【源码事实】

配套三个点：vendor/cordis/src/registry.ts:316 的 plugin( 是挂载入口；vendor/cordis/src/events.ts:32 的 DispatchMode 列出了 emit / parallel / serial / bail / waterfall 五种派发语义，:131 的 export class EventsService 是事件服务本体；vendor/cordis/src/service.ts:11 的 export abstract class Service 是所有 ctx.xxx 服务的基类。【源码事实】

读法建议：不要逐行读 fiber.ts。抓三个问题——插件挂载时发生了什么、卸载时怎么回收、服务冲突怎么报错。答完就走，细节留给 /cordis-lifecycle。

2. packages/boot/app-boot —— 知道"到底谁在跑" ​

读完 Cordis 你会立刻想问"那这棵树是谁定的"。答案在 profile。

packages/boot/app-boot/src/profile.ts 是 profile / bundle 清单的类型与解析入口。层叠顺序的权威描述在 docs/architecture.md:27："Layers apply to an empty entry list in this order"；代码形态在 apps/cli/src/profile-boot.ts:151 的 composeEntries([...])——四个数组的顺序和文档那句话一一对应。【设计记录】【源码事实】

顺带扫一眼 apps/cli/src/bin.ts:30 的 case 'profile': {（正常启动分支）和 apps/cli/src/profile-boot.ts:207 的 export async function runProfile。【源码事实】

读法建议：读完立刻跑一次 dsh --profile <你的 profile> --dump-config，把输出和 bundle/base/cordis.patch.yml 对照。这一步比读三个文件都有用。

3. packages/bundle/base —— 默认能力清单 ​

docs/architecture.md:25 说 dsh-base 是"first layer of every profile"（每个 profile 的第一层）。【设计记录】所以它的 cordis.patch.yml 就是"这个产品默认是什么"的清单。

读法建议：不用理解每一项，把它当目录看。看到不认识的插件名，回 /repo-map 用命名规律定位。15 分钟够了。

4. packages/core/session —— 先学"事实"，再学"流程" ​

这是全站最关键的顺序决定：先读 session，再读 agent-loop。

理由：agent-loop 的每一步都在往日志里写事件，如果你不先知道"事件有哪些种类"，读 agent.ts 时会被大量 append 调用淹没。反过来先读 session，agent.ts 就变成一条"依次追加哪些事件"的清晰线索。

先读 packages/core/session/src/types.ts:46 附近关于 SessionEvent 信封的说明（这是全站的词汇表），再读 packages/core/session/src/index.ts:604 的 append<T extends SessionEventType>( 签名，最后看 :792 的 export class SessionStore extends Service——注意它是 Cordis Service 的子类，正好印证第 1 步学的东西。【源码事实】

配套测试：packages/core/session/tests/session.spec.ts:903 附近的用例说明了追加与投影的边界行为。【测试行为】

读法建议：core/session/src/index.ts 很长，不要通读。只回答"哪些东西必须进日志、进去之后能不能改"。详见 /session-log。

5. packages/core/tools —— 模型的可见世界 ​

工具注册表决定模型"能看到什么"。packages/core/tools/src/index.ts:1037 的 register(definition: ToolDefinition): () => void 是注册入口。注意它返回一个反注册函数——这正是第 1 步在 Cordis 里学到的 disposer 约定在产品层的延续。【源码事实】

读法建议：抓两件事——工具是怎么注册进来的（谁调 register）、一次工具调用的结果是怎么变成日志事件的。40 分钟。

6. packages/core/agent-loop/src/agent.ts —— 主线，一次读完 ​

到这里前置全部就位，可以读主线了。docs/architecture.md:63 的 ## Turn flow 一节是回合流程的文档版描述。【设计记录】

agent.ts 只有 496 行，建议一次性读完，按调用顺序打点：:210 private async kick()（循环泵）→ :246 private async turn()，内部 :255 追加 turn/start → :225 preStep()，内部 :235 发 agent/pre-step → :332 private async step()，内部 :345 调 llm.stream(request)（唯一的模型接触面）→ :319 追加 turn/end。【源码事实】

配套：packages/core/agent-loop/tests/loop.spec.ts:198 附近是基本循环行为，tests/cancel.spec.ts:58 附近是取消语义，tests/interception.spec.ts:62 附近是"插件如何插手一步"。【测试行为】

读法建议：先用 grep -n "emit\|parallel\|serial\|bail\|waterfall" src/agent.ts 打出所有事件点，把它们抄成一条时间线，再回头读代码填空。详见 /one-turn。

7. tool-calls.ts + tool-calls.spec.ts —— 唯一必须"测试先行"的一步 ​

模型一次可能返回多个工具调用，怎么并发、怎么排队、失败怎么办——这段逻辑在 packages/core/agent-loop/src/tool-calls.ts，:59 的 export async function executeToolCalls( 是入口，:89 的 mode === 'parallel' 是分组判定。【源码事实】

但这一步请反过来读：先读 spec。 packages/core/agent-loop/tests/tool-calls.spec.ts:99 的 describe('tool-call scheduler: grouping and barriers', ...) 及其后 5 个 describe（乱序结算仍按模型顺序返回、并发池遵守上限、有序中间件、取消处理、失败静默）合起来就是一份调度器规格。【测试行为】读完 spec 再看实现，会快得多。

8. shell 三角 —— 一次学会剩下所有接缝 ​

AGENTS.md:109 定义接缝三角色，AGENTS.md:111 明确 dsh-shell 的 request/spec 拆分"is the template"。【设计记录】docs/architecture.md:98 的 ## Capability seams 一节是完整说明，:100 那句给出三个角色的定义并强调 "one role alone is not a seam"（单独一个角色不叫接缝）。【设计记录】

对读三个文件：packages/shell/shell/src/index.ts:40 的 declare module '@deepseek-ai/cordis'（Definition，看它怎么把 ctx.shell 挂上去）、shell/bash-local/src/index.ts（Provider）、shell/tool-bash/src/index.ts（Consumer）。【源码事实】

读法建议：这 40 分钟的回报最高——读完这一组，fs、llm、web、subagent 等 20 多个接缝你都能自己读懂。详见 /capability-seam。

9. packages/llm/llm —— 最小接缝，反向验证 ​

只有 5 个包的小组，但 docs/architecture.md:110 说加模型就是"register its adapter on ctx.llm"。【设计记录】

读法建议：把它当第 8 步的练习题——不看 shell，自己判断哪个是 Definition、哪个是 Provider（llm-deepseek / llm-pi-ai）、Consumer 在哪（提示：不是 tool-*，是 agent-loop 自己）。判断对了说明接缝模型你真会了。25 分钟。

10. packages/session/session-persistence —— 收尾：事实如何过夜 ​

packages/session/session-persistence/src/coordinator.ts:588 的 export class PersistenceCoordinator<TornMarker = unknown> 是协调器主体（那个 TornMarker 泛型是给“写到一半被打断的记录”留的位置）。【源码事实】磁盘结构版本在 packages/session/session-persistence-sqlite/src/schema.ts:20，当前 SCHEMA_VERSION = 15。【源码事实】

读法建议：只回答"崩溃后重启，哪些东西一定还在"。30 分钟。

读完这 10 个你处于什么位置：能画出启动链、能讲清一个回合、能自己读懂任何一个接缝、知道数据在哪。剩下 200 个包对你来说都变成了"某个已知模式的第 N 个实例"。【未验证判断】这是根据依赖链结构做的判断，不同背景的读者实际收敛速度会有差别。

六条按目标裁剪的路径 ​

选一条，只读列出的包。所有路径都假设你已完成上面前 10。

路径 A：我要加一个新工具（约 1.5 小时） ​

shell/tool-bash（抄结构）→ packages/core/tools/src/index.ts:1342 附近（注册契约）→ 目标能力的 Definition 包 → 该能力任一现成 tool-* 的 spec。

关键提醒：新工具应该是 Consumer，不要在工具里直接写执行逻辑。如果发现没有对应的 Definition，你要加的其实是一整个接缝，转路径 B。

路径 B：我要接一个新的执行环境 / 模型 / 搜索引擎（约 3 小时） ​

AGENTS.md:109–111 → docs/architecture.md:94–102 → packages/shell/shell 全组（9 个包，完整样板）→ 你的目标组 Definition → 对照一个现成 Provider 抄。

为什么要读整个 shell 组：只有 9 个包一起看，你才知道 Definition 里该放什么、Provider 之间怎么共享环境、Consumer 该多薄。

路径 C：我要改回合行为 / 加中间件（约 2 小时） ​

packages/core/agent-loop/src/agent.ts 全文 → tests/interception.spec.ts → tests/cancel.spec.ts → packages/guard/repeat-tool-reminder（一个真实的最小治理插件）。

关键提醒：先在 agent.ts 找到能满足你需求的现成事件点，绝大多数需求不需要改 agent.ts 本身。

路径 D：我要加自动注入的上下文（约 1 小时，最短路径） ​

packages/context/ 下四个包（agent-instructions、session-reference、time-context、tmux-context）→ agent.ts:279 的 agent/pre-step。

为什么最短：这四个包是同一模式的四个正例，挑最像你需求的抄。不要在 agent/pre-step 里直接拼字符串。

路径 E：我要排查会话丢失 / 恢复不对（约 2 小时） ​

packages/core/session/src/types.ts → src/index.ts:425 的 append → session-persistence/src/coordinator.ts:1123 → session-persistence-sqlite/src/schema.ts:20 → packages/core/agent-loop/tests/resume.spec.ts。

关键提醒：先分清"日志里没有"还是"日志里有但没落盘"还是"落盘了但投影不对"——三种问题在三个不同的包。

路径 F：我要加子 Agent / 委派（约 2.5 小时） ​

packages/subagent/subagent（Definition）→ subagent-fork-in-process（最容易懂的 Provider）→ packages/subagent/subagent/tests/service.spec.ts:71 的 describe('SubagentRuntime', ...)（注册/查找/启动/移除的完整语义）与 tests/continuation.spec.ts:170 的 describe('SubagentRuntime.startContinuable', ...)（可续跑的子 Agent）→ tool-subagent（Consumer）→ packages/jobs/（后台任务）。【测试行为】

关键提醒：subagent 组有 11 个包、7 种 Provider，先想清楚你要的是"全新子 Agent"还是"把一个回合委派出去"，两者选的 Provider 完全不同。

怎么判断自己读懂了 ​

不用做完整测验，问自己三句：

  1. 给一个陌生包名，能说出它在接缝三角里的角色吗？ 例如 web-search-exa、fs-observation-policy、ui-trajectory。
  2. 给一个需求，能说出该改哪个包吗？ 例如"工具执行超过 30 秒要报警"（提示：guard/timeout-policy，不是改 agent-loop）。
  3. 给一段行为，能说出去哪个 spec 验证吗？ 例如"两个工具调用是并发还是串行"（提示：tool-calls.spec.ts:99）。

三句都能答，就可以直接进四篇核心页深挖了。
