本页目录

Session log ​

这页解决什么问题 ​

/one-turn 里反复出现一个动作：this.session.append(...)。这页把这个动作拆开。

会话日志是 Harness 的唯一记忆。它不是"顺手存一份聊天记录"，而是一个硬性设计约束的落点：docs/architecture.md:96 的 Model-visible means logged——任何进入模型请求的东西都必须能从日志重建，并且有运行时不变量在断言这件事。【设计记录】AGENTS.md:107 用一个更强的写法表达同一件事：Model-visible ⟺ logged。【设计记录】

这页解决四件事：（一）append-only 到底强制到什么程度；（二）append() 的五道校验分别在防什么；（三）模型历史是怎么从日志投影出来的；（四）SESSION_FORMAT_VERSION 与 SCHEMA_VERSION 各自版本化什么。

不在本页范围内：回合怎么推进（见 /one-turn）、压缩与溢出策略、某个具体持久化后端的表结构细节。

先用人话解释 ​

Session 的本体就是一个数组，只能往后加。 packages/core/session/src/index.ts:418 的类注释一句话说完：An event-sourced session: an append-only log of SessionEvents（事件溯源的会话：一份 SessionEvent 的只追加日志）。【源码事实】类声明在 :425。

每一行叫一条 SessionEvent，它有固定的信封。 类型定义在 packages/core/session/src/types.ts:404：每条事件带 type、seq、time、data，外加可选的表层元数据。写入口只有一个：packages/core/session/src/index.ts:604 的 append<T extends SessionEventType>(...)。【源码事实】

写进去之后就改不了了——这是被代码强制的，不是靠自觉。 append() 会先给数据做 JSON 快照（:614），再把整条事件深冻结（:627 的 const event = deepFreeze({）。【源码事实】

模型看到的历史是"从日志现算的投影"，不是存着的数组。 投影函数是 :726 的 deriveMessages(): Message[]，它每次返回一个新的数组快照（:746 的 return [...this.derived]）。【源码事实】

"落账"和"落盘"是两件事。 append() 只保证进了内存里的日志并广播了 session/event（:76）。真正落到磁盘要靠持久化插件订阅这个事件攒批写；需要"此刻必须已经在磁盘上"的地方，得显式调 ctx.sessions.flush(session)（:1022）。

日志里可能出现"这个 build 不认识的事件类型"。 这时的规则是：默认拒绝重建会话，除非写入方在信封上标了 ignorable: true。packages/core/session/src/types.ts:414 的原话是 Absent means required（不标就是必需）。【源码事实】

智能工厂比喻 ​

沿用本站统一映射（完整对照见 /glossary）。

只能追加的生产流水账 = session log。 工长每做一件事就往账上写一行，只能追加，不能改、不能删、不能插队。

一条生产事实 = SessionEvent。 账上的一行：几点几分、什么事、细节是什么。行号就是 seq。

往账上写一行 = append()。 写之前有几道核对：这行内容能不能规范抄写（JSON 化）、行号是不是接着上一行、这一行要不要出现在对外账单上。核对过了就用不可擦的笔写下去（深冻结）。

账房 = SessionStore（ctx.sessions）。 管着所有活着的账本：开新账（:830 create）、复印分叉（:1081 fork）、销毁。

从流水账现算一份对账单 = deriveMessages()。 模型每次要看历史，账房不是把上次那份对账单递过去，而是照着流水账重新算一份。

把流水账抄进正式账册 = 持久化。 抄账的人订阅"账上有新行"的通知，攒一批再抄进正式账册（SQLite）。

"现在必须已经抄完" = flush()。 有些节点（比如把单子递给外部大脑之前）要求正式账册必须已经跟上，这时就喊一声停下来等抄完。

比喻的限制 ​

第一，"流水账"暗示只有一种读法，实际上账本之上还有一层"表层"。 不是每条事件都会出现在模型历史里。packages/core/session/src/types.ts:343 定义了 export type SurfaceEventType，packages/core/session/src/surface.ts:398 的 export class SurfaceManager 单独管这层"哪些事件构成对外可见序列"，append() 每次都要过它的 validateNext(event)（surface.ts:421）。【源码事实】所以 deriveMessages() 遍历的是 surface.nodes（packages/core/session/src/index.ts:735 的 nodes.slice(this.derivedNodes)），不是全部事件。把日志当成"聊天记录的逐行版"会解释不了这一层。

第二，"不可擦的笔"比比喻更狠：连你手上那份对账单都是冻的。 :627 的 deepFreeze 冻的是整条事件，packages/core/session/tests/session.spec.ts:903 的 deep-freezes seeded and appended event snapshots 断言这件事；:437 的 isolates the log from mutation through a derived message (append-only contract) 进一步断言你拿到的派生消息也不能反过来污染日志。【测试行为】工厂比喻里"抄一份给你随便改"在这里不成立。

第三，"抄账"不是同步动作，而且失败会被显式拒绝。 持久化协调器订阅 session/event 后是攒批异步写（packages/session/session-persistence/src/coordinator.ts:1123）。这就意味着"账上有了"不等于"盘上有了"。需要强一致的地方由 packages/session/session-checkpoint-policy 插进去：:35 在构造模型流之前 await ctx.sessions.flush(session)，:70 在顶层工具体之前、:79–:80 在每次 agent/pre-step 之前各 flush 一次。【源码事实】

第四，"账本版本"其实是两个正交的数字。 比喻里"账本换了个格式"是一件事，源码里是两件：packages/core/session/src/types.ts:56 的 export const SESSION_FORMAT_VERSION = 0 版本化事件词表且按 session 存，packages/session/session-persistence-sqlite/src/schema.ts:20 的 export const SCHEMA_VERSION = 15 版本化磁盘表结构。【源码事实】一个停在 0、一个已经 15，不是谁忘了改。

第五，"看不懂的一行跳过就好"是错的。 比喻里遇到看不懂的账目可以先放着。源码里默认必须拒绝：packages/core/session/src/types.ts:414 的 Absent means required，packages/session/session-persistence/src/coordinator.ts:1063 的 if (KNOWN_SESSION_EVENT_TYPES.has(event.type) || event.ignorable === true) continue——不在已知集合里、又没标 ignorable，下一行就抛错。【源码事实】

常见误解 ​

误解一："session log 就是聊天记录。" 不是。聊天记录只是它的一种投影。同一份日志还能投影出转录、遥测、UI 时间线。而且它的粒度细得多——连每个流式分片（packages/core/agent-loop/src/agent.ts:349 的 assistant/chunk）都单独一行。【源码事实】

误解二："deriveMessages() 返回的是内部数组，改它很危险 / 改它能改历史。" 两句都不对。它每次返回 [...this.derived]（packages/core/session/src/index.ts:746）这份新数组，所以改它既不会影响日志，也不会影响别人拿到的那份。packages/core/session/tests/session.spec.ts:437 专门断言这条 append-only 契约。【源码事实】【测试行为】不过数组里的 Message 对象是共享且深冻结的，想改内容只能重建。

误解三："append() 成功了就等于写到磁盘了。" 不等于。append() 之后是异步攒批（packages/session/session-persistence/src/coordinator.ts:1123）。要"此刻已在盘上"必须走 ctx.sessions.flush(session)（packages/core/session/src/index.ts:1022），而这件事在 Harness 里由 packages/session/session-checkpoint-policy 统一插在三个位置（:35、:70、:79）。【源码事实】

误解四："SESSION_FORMAT_VERSION 停在 0 是没人维护。" 是显式策略。AGENTS.md:7 写着：发布前没有外部消费者，宁可要正确的地基而不是兼容垫片；后端拒绝旧的磁盘格式，SQLite 用单调递增的 SCHEMA_VERSION，而 dsh-session 把 SESSION_FORMAT_VERSION 保持在 0 且不做兼容承诺。【设计记录】另外 AGENTS.md:104 补了一句关键限定：只有结构性的格式变化才 bump 它——加一种新事件类型通常不需要。

误解五："SCHEMA_VERSION 和 SESSION_FORMAT_VERSION 是一个东西的两处写法。" 正交。前者是 SQLite 表结构版本（packages/session/session-persistence-sqlite/src/schema.ts:20），换持久化后端就没它的事；后者按 session 存、版本化事件词表（packages/core/session/src/types.ts:56），会话头的校验在 packages/core/session/src/index.ts:102。【源码事实】

误解六："遇到不认识的事件类型跳过就行。" 默认必须拒绝。packages/core/session/src/types.ts:414 的 Absent means required，packages/session/session-persistence/src/coordinator.ts:1063 是执行点。【源码事实】只有写入方明确标了 ignorable: true（这一列真的落盘，schema.ts:144）才允许跳过。这是"新版本写的日志被旧版本读到"时唯一安全的口子。

误解七："每条事件都会进模型历史。" 不会。进历史的只有表层事件（packages/core/session/src/types.ts:343 的 SurfaceEventType），deriveMessages() 遍历的是 surface.nodes（packages/core/session/src/index.ts:735）。【源码事实】

三道自测题 ​

第一题：某人给一条 session event 的 data 里塞了一个 Date 对象和一个自定义类实例。他本地跑通了，因为"打印出来是对的"。上线后 CI 报错。哪一行拦住了他？如果他改成 data.time = new Date().toISOString() 呢？

参考答案

拦住他的是 packages/core/session/src/index.ts:614–:616：const dataSnapshot = snapshotJsonValue(data)，返回 undefined 就 throw new Error(...)，错误文案是 carries non-JSON-serializable data。【源码事实】实现在 packages/core/session/src/json.ts:177。

第二题：你实现了一个新功能，往日志里加了一种事件 myplugin/note。同事担心"以后旧版本 dsh 读到这条会崩"。什么情况下会崩？什么情况下不会？你需要 bump SESSION_FORMAT_VERSION 吗？

参考答案

会崩的情况：旧 build 的 KNOWN_SESSION_EVENT_TYPES（packages/core/session/src/known-event-types.ts:19）里没有 myplugin/note，而这条事件的信封上又没有 ignorable: true。 执行点是 packages/session/session-persistence/src/coordinator.ts:1063：if (KNOWN_SESSION_EVENT_TYPES.has(event.type) || event.ignorable === true) continue，两个条件都不满足就抛错，拒绝解释这份日志。【源码事实】

不会崩的情况：你在写入时标了 ignorable: true。 packages/core/session/src/types.ts:414 的语义是 Absent means required——不标就是必需的，标了才表示"不认识可以安全跳过"。【源码事实】这个标记不是运行期猜的，它随事件一起落盘（SQLite events 表有 ignorable 列，packages/session/session-persistence-sqlite/src/schema.ts:144）。【源码事实】

判断标准是语义，不是省事：如果缺了这条事件模型上下文就不完整（例如它承载模型可见内容），那它必须是 required，让旧 build 明确拒绝，而不是悄悄给出一份缺内容的历史——这正是 Model-visible ⟺ logged（AGENTS.md:107）在版本演进上的推论。【设计记录】

通常不需要 bump SESSION_FORMAT_VERSION。 AGENTS.md:104 明确限定：只有结构性的格式变化才 bump；加一种事件类型靠的是 required/ignorable 这套读侧机制，而不是版本号。【设计记录】而且它现在的策略值就是 0 且不做兼容承诺（AGENTS.md:7、packages/core/session/src/types.ts:56）。

第三题：一个插件在 session/event 监听里做了这件事：发现是 assistant/message，就立刻读 session.deriveMessages() 拿最后一条消息做统计。它在大多数情况下工作正常，但偶尔统计到的最后一条不是刚刚那条。为什么？如果它需要"这条一定已经在磁盘上"，应该怎么做？

参考答案

因为 session/event 的回调时机与"表层是否已经把它算成一个节点"是两件事。

append() 的顺序是：:641 先收齐监听者 → :643 this.log.push(...) → :646 才真正调用观察者。【源码事实】所以回调时事件确实已经在日志里了。但 deriveMessages() 遍历的是表层节点（:735 的 nodes.slice(this.derivedNodes)），而 packages/core/session/src/index.ts:726 的文档注释说明了两件会让"最后一条"不如预期的事：一是内容为空的 assistant/message（例如只承载 usage 的 max-tokens 步）投影为 null、不进历史；二是表层被 replace 重写时（surface.ts:432 的 replaceGeneration 变化）整份投影会重建。【源码事实】所以"日志里最后一条事件"和"投影里最后一条消息"不是同一个东西——这也正是 docs/agent-lifecycle.md 那条"空内容留在耐久事件里、不进派生历史"的规则。

正确做法：要统计就针对事件本身（回调的第二个参数就是那条冻结的事件），不要绕道去读投影。

要"一定已经在磁盘上"，必须 await ctx.sessions.flush(session)（packages/core/session/src/index.ts:1022）。它派发 session/flush（:85、:1025）并用 Promise.allSettled 等所有耐久性监听者结算（:1026）；协调器在 packages/session/session-persistence/src/coordinator.ts:1129 排空缓冲。【源码事实】更好的做法是别自己插 flush，而是照 packages/session/session-checkpoint-policy/src/index.ts 的方式把它放在有意义的边界上（:35 模型流之前、:70 顶层工具体之前、:79 每次 pre-step 之前），三个位置各有测试（session-checkpoint-policy.spec.ts:63、:120、:225）。【测试行为】
