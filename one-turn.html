一次 Turn ​

这页解决什么问题 ​

看完 /cordis-lifecycle 你知道插件怎么挂上去了，但还不知道它们凑在一起到底在推进什么。

答案是一个循环：拿到输入 → 问模型 → 模型可能要求调工具 → 调完再问 → 直到没有欠账。这个循环的默认实现只有一个文件是主角：packages/core/agent-loop/src/agent.ts 里的 export class ReactLoopAgent implements Agent {（:64）。【源码事实】

这页解决三件事：（一）说清 turn 和 step 到底怎么划分；（二）把一次 turn 走过的事件按真实顺序排出来，并指明每个拦截点是 waterfall 还是 serial；（三）说明模型看到的历史是从哪里来的。

不在本页范围内：日志怎么落盘、版本号怎么管（见 /session-log）；某个工具背后的能力为什么要拆三个包（见 /capability-seam）。

先用人话解释 ​

step 是"一次模型请求，加上这次请求引发的工具调用"。 docs/architecture.md:65 的原话：A step is one model request plus the tools it calls。【设计记录】

turn 是"零个或多个 step"。 同一行还说：它在第一份输入被领走之前打开，在没有欠账（nothing is owed）时关闭。【设计记录】所以一次 turn 里可能问了模型三次——每次问都是一个 step。

"零个 step 的 turn"是合法的。 输入被拦截器拒绝、或者被改写成空，turn 照样开一次、关一次，让日志留下这次尝试的痕迹。

所有输入只有一个入口：inbox。 docs/architecture.md:86：Input reaches the driver through one inbox。【设计记录】有的消息会立刻唤醒驱动（比如你敲的那句话），有的只是"注入的上下文"，要等下一条会唤醒的消息把它一起带出去。

模型看到的历史不是一个数组变量，是现算的。 packages/core/agent-loop/src/agent.ts:341 把 this.session.deriveMessages() 当参数传进 buildRequest。【源码事实】每一步都从会话日志重新投影一次。

每一步的关键节点都开了口子给插件。 有两个特别重要：agent/pre-step 决定"模型这一步看到什么"，agent/request 决定"这一步用哪个 provider 和哪个 model"。两个都是 waterfall，监听者可以改写内容，但必须调 next() 才往下传。

智能工厂比喻 ​

沿用本站统一映射（完整对照见 /glossary）。

任务工长 = Agent。 它拿着一个会话，决定现在该问模型什么、模型说要用哪台机器、结果拿到后接着干还是收工。

工单 = turn。 工长开一张单，单子上可能有一道工序，也可能有五道，也可能开完就作废。

工序 = step。 一道工序 = 一次问模型 + 这次模型要求动的那几台机器。

待办篮 = inbox。 所有进来的纸条都先落在篮子里。有的纸条一落进去就把工长叫醒，有的（注入的上下文）只是躺着，等下一张会叫醒工长的纸条把它一起带走。

出工前的会签单 = agent/pre-step。 工长准备开工序之前，把"这道工序要给模型看什么"做成一张单子，依次给各科室盖章。任何科室都能改内容，也能直接作废这张单子。

派单前确认用哪个大脑 = agent/request。 同样是会签单，签的是"这次问哪个模型、用什么参数"。

流水账 = session log。 工长每做一件事就往账上追加一行：开单、开工序、口述记录、整理成文、派工单、完工单、关工序、关单。

收工前最后一次通知 = agent/turn-stopping。 工长要关单了，先按顺序通知一圈相关科室。注意这一张不是会签单，见下一节。

比喻的限制 ​

第一，agent/turn-stopping 不是会签单，是"按顺序挨个通知"。 这是本页最容易记错的一处。packages/core/agent-loop/src/agent.ts:296 的调用是 await this.dispatch.serial('agent/turn-stopping', { turn, signal })——serial，不是 waterfall。【源码事实】类型声明也对得上：packages/core/agent/src/runtime-types.ts:278 的 'agent/turn-stopping'(this: Scoped<Agent>, payload: {...}): Promise<void> | void 签名里根本没有 next 参数，而同文件 :231 的 'agent/pre-step'、:244 的 'agent/request'、:260 的 'agent/request-error' 都带 next: () => Promise<...>。【源码事实】docs/architecture.md:84 把这件事写成一句话：agent/turn-stopping is serial and has no next()。【设计记录】把 serial 当 waterfall 写会直接抛错，把 waterfall 当 serial 写会让整条链断在你这儿。

第二，工具执行不是单线传送带。 比喻暗示工序一个接一个。真实实现里有调度器：packages/core/agent-loop/src/tool-calls.ts:88 先用 ctx.tools.executionMode(first.exec).kind 判定这一组调用的模式，再交给 :90 的 runGroup(。【源码事实】并行安全的兄弟调用会同时开跑：packages/core/agent-loop/tests/tool-calls.spec.ts:99 的 describe('tool-call scheduler: grouping and barriers', ...) 第一条用例（:100）就叫 runs parallel-safe siblings concurrently (all start before any completes)——断言的是"全部开始之后才有任何一个完成"。【测试行为】

第三，"工长的记性"其实是每次现算的。 比喻里工长脑子里记着刚才发生了什么。真实实现里 packages/core/agent-loop/src/agent.ts:341 每一步都调 this.session.deriveMessages() 重新投影一遍。【源码事实】这条设计有一条硬约束支撑：docs/architecture.md:96 的 Model-visible means logged——任何进入模型请求的东西必须能从日志重建。【设计记录】所以"我在监听器里临时拼一段文本塞进请求"是违规操作。

第四，"关单"不总是因为活干完了。 packages/core/agent-loop/src/agent.ts:319 追加 turn/end 时带的是 { turn, reason: turnEnds! }——turn 的结束一定带一个原因。【源码事实】原因可能是正常结束、aborted（packages/core/agent-loop/tests/loop.spec.ts:945）、也可能是 max-tokens（:963）。【测试行为】工厂比喻里"单子关了"是一个状态，这里它是一条带因果的账目。

第五，"账本"和"工长手上的活对象"是两回事。 turn/step/user/assistant/tool 这些是耐久的 session event，重启后还在。而 agent/* 事件携带的是活的 Agent 对象（inbox、status、request 等），它们不进日志、重启即消失。混淆这两类是新读者最常犯的错。

以下全部使用真实术语。

常见误解 ​

误解一："一次用户输入等于一个 step。" 不是。一次输入开一个 turn，turn 里可能有零个、一个或多个 step。docs/architecture.md:65 的定义是 step = 一次模型请求加它调的工具。【设计记录】模型连续调三轮工具，就是三个 step、一个 turn。

误解二："agent/turn-stopping 是 waterfall，我照 agent/pre-step 的写法抄就行。" 抄错了会直接坏。packages/core/agent-loop/src/agent.ts:296 用的是 dispatch.serial，packages/core/agent/src/runtime-types.ts:278 的签名里没有 next。【源码事实】serial 监听者拿不到也不该调 next()。

误解三："在 agent/pre-step 里改写 messages 是加上下文的正道。" 只有当你改写的内容已经在日志里才成立。docs/architecture.md:96 的 Model-visible means logged 要求任何进入请求的内容可从日志重建。【设计记录】想加模型可见的上下文，正道是 agent.inject()（它会落 agent/inbox/spliced，packages/core/agent/src/inbox.ts:186）或者新增一种 session event，而不是在监听器里凭空拼字符串。

误解四："assistant/chunk 只是给 UI 用的，可以不落账。" 它是耐久事件，packages/core/agent-loop/src/agent.ts:349 逐片 append 并收集 seq，:382 的 assistant/message 用 sourceEventSeqs 指回去。【源码事实】这条链路是回放保真与转录的基础，不是 UI 的附属品。

误解五："工具是一个一个跑的。" 不是。packages/core/agent-loop/src/tool-calls.ts:88 判定执行模式，:90 的 runGroup( 做分组并发，测试 tool-calls.spec.ts:100 断言并行安全的兄弟调用全部先启动再完成。【测试行为】同时它也不是"全都并发"：exclusive 的调用会形成屏障，这也是同一个 describe（:99）覆盖的语义。

误解六："turn 被取消了就不会有 turn/end。" 会有，而且带原因。packages/core/agent-loop/src/agent.ts:319 追加 turn/end 时必须给 reason；packages/core/agent-loop/tests/loop.spec.ts:945 断言中途取消得到 aborted 这个原因。【测试行为】"每个出口都要给 turn 一个结束原因"是这段代码的显式意图。

误解七："agent/request 决定请求内容。" 它决定的是调用配置（provider、model 等，返回类型是 LlmCallConfig，见 packages/core/agent/src/runtime-types.ts:244）。【源码事实】请求里的历史来自第 11 跳的 deriveMessages()，两件事分开。

三道自测题 ​

第一题：日志里出现了这样一段：turn/start → turn/end，中间一个 step/start 都没有。这可能吗？如果可能，最可能是什么原因，哪一行源码/文档支持你的判断？

参考答案

可能，而且是刻意设计的。 这叫零步 turn。

docs/architecture.md:88 写得很明确：agent/pre-step 的监听者可以改写领到的消息，也可以直接拒绝；被拒绝或为空的首次领取仍然会关掉一个耐久 turn，好让日志记录下这次尝试。【设计记录】

对应源码是 packages/core/agent-loop/src/agent.ts:234–:235 的 agent/pre-step waterfall：它的返回值 decision 决定要不要走到 :279 的 append('step/start', ...)。如果决定不进入，:319 的 turn/end 仍然会在 finally 语义下落账。【源码事实】

测试侧的相关证据：packages/core/agent-loop/tests/loop.spec.ts:913 的 a throwing agent/pre-step listener fails the proposal, not the loop——提案失败，循环不倒。【测试行为】另一个相关但不同的场景是 :640 的 inject() while idle durably stages context without opening a turn：注入上下文时连 turn 都不开，这和"开了 turn 但没有 step"是两种不同的日志形态，别混。【测试行为】

第二题：你要实现"每次回合结束时把这一轮的 token 用量写进一份统计文件"。同事建议挂 agent/turn-stopping。这个选择合理吗？你的监听器函数签名该长什么样？如果你在这个监听器里给 Agent 又塞了一条消息，会发生什么？

参考答案

选择合理，但要清楚它的三条性质。

一，它是 serial，不是 waterfall。 packages/core/agent-loop/src/agent.ts:296 是 await this.dispatch.serial('agent/turn-stopping', { turn, signal })。【源码事实】签名照 packages/core/agent/src/runtime-types.ts:278 写：(payload: { agent, turn, signal }) => Promise<void> | void，没有 next，不要写、也不要调。【源码事实】

二，它是 await 的。 serial 会逐个等待（vendor/cordis/src/events.ts:204 的 async serial(...args: any[])），所以你在这里做慢 I/O 会拖长回合收尾。【源码事实】

三，在这里塞消息会让回合继续，而不是报错。 这是官方支持的模式：packages/core/agent-loop/tests/loop.spec.ts:766 的 agent/turn-stopping can steer another step (/loop pattern) 断言的正是"收尾通知里被塞了活，于是又开一个 step"。【测试行为】对应主图里 STOP --> PRE 那条回边。所以如果你只想统计、不想改变控制流，就不要在这里调 inject() / steer()。

顺带一句：真要做用量统计，assistant/message（packages/core/agent-loop/src/agent.ts:382）本身就带 usage，docs/agent-lifecycle.md:74 说它记录每一次成功的 provider 调用（含空内容与 max-tokens 收尾）——从日志算比在收尾时抓更可靠。【设计记录】

第三题：模型在第 1 个 step 里要求调 3 个工具，其中 2 个是只读检索、1 个是写文件。第 2 个 step 的请求里，模型能看到这 3 个结果吗？这 3 个结果的日志顺序由什么决定，执行顺序又由什么决定？两者一致吗？

参考答案

能看到。 路径是：结果先落账（packages/core/agent-loop/src/tool-calls.ts:281 的 session.append('tool/result', {），下一个 step 在 packages/core/agent-loop/src/agent.ts:341 调 deriveMessages() 时从日志重新投影出来。【源码事实】结果不是被直接塞进请求的，这一点是 docs/architecture.md:96 的 Model-visible means logged 的直接体现。【设计记录】

执行顺序由调度器决定。 packages/core/agent-loop/src/tool-calls.ts:88 用 ctx.tools.executionMode(first.exec).kind 判定模式，:90 的 runGroup( 分组：并行安全的可以同时开跑（tool-calls.spec.ts:100 断言 all start before any completes），exclusive 的会形成屏障（同一个 describe，:99）。【测试行为】所以两个只读检索很可能是并发的，写文件那个大概率被隔开。

日志顺序不等于完成顺序。 :134 的 const callSeqs: number[] = group.map(() => -1) 保留每个 tool/call 的 seq，结果提交时引用回它——这套设计的目的正是按模型给出的顺序提交结果，而不是按谁先跑完提交。所以：执行可以乱序并发，账面顺序稳定。

一句话总结两者的关系：执行顺序服从调度器，账面顺序服从模型给的调用顺序，模型看到的顺序服从账面。 【跨源码分析】
