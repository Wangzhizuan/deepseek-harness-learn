一页理解 Harness ​

这页解决什么问题 ​

你打开 DeepSeek Harness 仓库，看到 packages/ 下 49 个分组目录、219 个 package、vendor/ 里另一个完整框架、docs/ 里几十篇英文文档。你想知道的其实只有三件事：它是什么？它由哪几块组成？一个请求进来后怎么走完？

这页就回答这三件事，不多不少。读完你应该能对着仓库指出五六个关键文件，并说出它们各自负责什么。深入某个子系统请走 /one-turn、/session-log、/capability-seam、/cordis-lifecycle；找具体源码位置请走 /repo-map 和 /source-order。

先用人话解释 ​

Harness（马具 / 承载框架）就是"包在大模型外面、让它能真的干活的那一整套东西"。

模型本身只会做一件事：给它一段文字，它吐回一段文字。它不会读文件、不会跑命令、不会记住上次说过什么、不会在你按下 Ctrl-C 时停手。这些全部是 Harness 的活。

具体说，DeepSeek Harness 负责这些事：

  • 把散落的"上下文"（系统提示、可用工具的描述、历史对话、当前目录信息）拼成一次模型请求。
  • 接住模型流式吐回的内容，把它拆成"文本块"和"工具调用请求"。
  • 真的去执行那些工具调用——跑 shell、读写文件、搜网页、开子 Agent——并把结果送回给模型。
  • 判断"这一轮结束了吗"：模型还想继续调工具就再来一步，没事干了就收尾。
  • 把上面每一个事实按顺序写进一本只能追加的账本，这样你重启、分叉、回放、导出都还原得出来。

DeepSeek Harness 的特别之处，是它把上面每一块都做成了插件。项目根目录的 AGENTS.md:3 第一句就写着这是 "a plugin-based agent harness on vendored Cordis: everything is a plugin"，并且明确要求改 packages/ 之前先读 docs/architecture.md。【设计记录】

"一切皆插件"不是口号。官方架构文档 docs/architecture.md:11 说得更直白：模型适配器、工具注册表、会话日志、乃至 agent loop 本身都是插件，所以每一块都能从配置里换掉；:13 补一句"没有一个特权核心可以打补丁"——你扩展 dsh 的方式是在其他插件旁边再挂一个插件。【设计记录】

支撑这件事的框架叫 Cordis，它不在 node_modules 里，而是被 vendored（内联）到本仓库的 vendor/cordis，作为 pnpm workspace 成员一起构建。

智能工厂比喻 ​

把 DeepSeek Harness 想成一座智能工厂。

厂区公共设施与连接系统就是 Cordis 的 Context（vendor/cordis/src/context.ts:42 的 export class Context {）。水电气、传送带、广播系统都在这儿。任何设备接上它就能用到全厂的资源，也能对全厂广播。

可插拔工作站就是 plugin。每个工作站有自己的接口规格，推到厂区里插上就开始工作，拔掉就干净地消失——它铺过的临时管线、订阅过的广播、占用过的编号全部回收。负责记住"这台工作站到底占了什么、拔掉时要还什么"的账本叫 Fiber（vendor/cordis/src/fiber.ts:184 的 export class Fiber {）。注意：一台工作站型号可以在厂里插好几台，每插一次产生一个 Fiber，所以 Fiber 是"工作站的一次运行实例"，不是型号本身。

工厂方案和设备套装就是 profile 和 bundle。docs/architecture.md:17 说一个运行中的 dsh 是"a plugin tree composed at boot from ordered layers"（启动时由有序层级组装出的插件树）。profile 是存在 Harness home 里的一份具名组装方案（:19），列出它要叠哪些 bundle；bundle 是配置行加代码的分发格式（:21），像一箱预配好的设备套装。web 和 headless 是随仓库发布的两个方案模板。【设计记录】

统一能力接口就是 Service Definition，真正提供能力的机器就是 Provider，使用能力的岗位就是 Consumer。比如"执行 shell 命令"这个能力：接口写在 packages/shell/shell，本机执行的机器是 packages/shell/bash-local，沙箱里执行的机器是 packages/shell/bash-sandbox，而模型能看见并调用的那个岗位是 packages/shell/tool-bash。换机器不换岗位，岗位完全感觉不到。

任务工长就是 Agent。它拿到一个任务，决定"现在该问模型什么、模型说要用哪台机器、结果拿到后接着干还是收工"。工长的调度流程就是 Agent loop，实现在 packages/core/agent-loop。

只能追加的生产流水账就是 Session log。工长每做一件事就往流水账上追加一行，只能追加，不能改、不能删。账上的每一行叫一条 Session event（一条生产事实）。整个工厂的"记忆"就是这本账，模型每次看到的历史都是从这本账现算出来的。

比喻的限制 ​

工厂比喻能让你进门，但它在四个地方会明确失真。这段专门点明，之后本页回到真实术语。

第一，并发不像流水线。 工厂比喻暗示工序一个接一个。真实的工具调用是有调度器的：模型一次可以要求调多个工具，packages/core/agent-loop/src/tool-calls.ts 里的调度器会判断哪些能并行、哪些必须串行、哪里要设屏障（barrier）。测试文件 packages/core/agent-loop/tests/tool-calls.spec.ts:99 的 describe('tool-call scheduler: grouping and barriers', ...) 第一条用例就叫 "runs parallel-safe siblings concurrently (all start before any completes)"——它断言并行安全的兄弟调用全部开始之后才有任何一个完成。【测试行为】所以别把工具执行想成一条单线传送带。

第二，"广播"其实分五种模式，别混。 vendor/cordis/src/events.ts:32 定义 export type DispatchMode = 'emit' | 'parallel' | 'serial' | 'bail' | 'waterfall'。【源码事实】其中两种最容易搞错：waterfall（瀑布）的监听者拿到值可以改写再往下传，必须调用 next() 才能把控制权交给下一个；serial（串行）只是按顺序跑完，没有 next()。docs/architecture.md:84 明确列出哪些是 waterfall：agent/pre-step、agent/request、llm/stream 和三个 tools/*；而 agent/turn-stopping 是 serial。【设计记录】工厂里"喊一声大家都听见"的直觉在这里不够用——waterfall 更像一份依次盖章、每个人都能改内容的会签单，漏盖一个章（不调 next()）流程就断在那儿。

第三，生命周期不是"装上就一直在"。 真实工厂里设备装了就长期在那。Cordis 的插件可以随时卸载，而且卸载必须可逆：它注册的服务、事件监听、定时器都是"效果"（effect），随 Fiber 一起回收。这套机制是 Cordis 最需要单独学的部分，见 /cordis-lifecycle。

第四，"账本"和"现场状态"是两回事（live state vs durable state）。 流水账上的一行（Session event）是持久事实，重启后还在，会通过 session/event 广播出去。但工长手上正在处理的那个活对象（live Agent，通过 agent/* 事件传递：inbox、step、status、request 等）只存在于内存，它不进账本。docs/architecture.md:57-58 把这两类事件分得很清：需要活过重载的事实用 session event，观察或拦截"正在进行中的工作"用 agent event。【设计记录】把这两个混起来是新读者最常见的错。

以下段落全部使用真实术语。比喻和真实术语的完整对照见 /glossary。

真实概念和结构图 ​

图说明：最上层是 profile 与 bundle 组成的配置层，它在启动时把插件树装配进 Cordis Context。Context 之下并列挂着四个核心插件：core/agent-loop（回合驱动）、core/session（只追加日志）、core/tools（工具注册表与执行管道）、llm/llm（模型接缝）。agent-loop 同时依赖另外三者：向 session 追加事实、向 tools 派发调用、向 llm 发请求。tools 之下是各个具体能力接缝（shell、fs、web 等），session 之下是持久化插件负责落盘。

完整版（节点较多，可放大查看）

完整版图说明：这张图把启动链路和运行期插件树画在一起，节点标签为了不撑破正文栏都用了短名，完整路径见下。左上从 apps/cli/src/bin.ts（dsh 命令入口）开始，经 apps/cli/src/profile-boot.ts 与 packages/boot/app-boot 解析出 profile，展开成 bundle/base、bundle/web-app、bundle/headless 等 bundle 层（图里的 bundle/base 等）；每一个配置行通过 cordis 的 registry.plugin() 挂载，每次挂载产生一个 Fiber，所有 Fiber 共享一棵 Context 树。Context 上并列注册着 core/agent、core/agent-loop、core/session、core/tools、core/system-prompt、llm/llm 六个核心插件。llm/llm 之下挂具体模型 Provider（如 llm-deepseek）；core/tools 之下挂 21 个 tool-* Consumer 包，其中 tool-bash 透过 shell/shell 接口打到 bash-local 与 bash-sandbox 两个并列 Provider（图里画成两个分支）；core/session 之下由 session-persistence 协调器分发到 SQLite 后端（session-persistence-sqlite，其 SCHEMA_VERSION 为 15）或 JSONL 后端（session-persistence-jsonl）；Context 上还挂着 host/webserver 以及它带起来的 client/* 前端插件族。

turn 与 step 的定义 —— docs/architecture.md:65 是权威表述：一个 step 是"一次模型请求加上它调的那些工具"；一个 turn 是零个或多个 step，"在它的第一份输入被领走之前打开，在没有任何欠账时关闭"。注意 turn 可以有零个 step——被 agent/pre-step 拒绝的输入依然会开一个 turn 再关掉，好让日志留下这次尝试的痕迹。【设计记录】

能力接缝（capability seam） —— docs/architecture.md:100 定义为"a swappable capability with three roles"：Service Definition 声明接口、Service Provider 实现它、Consumer 使用它（通常是模型可见的工具）。AGENTS.md:109 把这条写成了硬规则：接缝必须三个角色齐全，单独一个角色不叫接缝。AGENTS.md:111 进一步指定 dsh-shell 的 request/spec 拆分是这类设计的模板。【设计记录】packages/shell/shell/src/index.ts:40 的 declare module '@deepseek-ai/cordis' 块就是接口如何往 Context 上声明 ctx.shell 的范例。【源码事实】

"模型看得见就必须记下来" —— docs/architecture.md:96 的 Model-visible means logged：任何进入模型请求的东西都必须能从日志重建，而且有运行时不变量在断言这件事。所以加一种新的模型可见输入，必然要加一种新的 session event。【设计记录】

常见误解 ​

误解一："agent loop 是核心，其他都是外围插件。" 不是。docs/architecture.md:11 明确把 agent loop 本身列为可替换插件，:13 说"没有特权核心"。packages/core/agent（8 个包的 core 组之一）定义的是 Agent 接口，packages/core/agent-loop 只是默认驱动。你可以挂一个别的驱动实现同一接口。【设计记录】

误解二："session log 就是聊天记录。" 不是。它是产生模型上下文的唯一来源，聊天记录只是它的一种投影。deriveMessages()（packages/core/session/src/index.ts:726）是投影函数，同一份日志还能投影出转录、遥测、UI 时间线。而且它记的粒度比聊天记录细得多——连每个流式分片（assistant/chunk）都单独一行。【源码事实】

误解三："改一个工具就是改那个工具的包。" 大概率不够。一个能力是三角（AGENTS.md:109），改行为要先判断你动的是接口、实现还是消费方。改接口会同时影响所有 Provider 和 Consumer。【设计记录】

误解四："vendor/cordis 是第三方依赖，不用管。" 它是 pnpm workspace 成员，和 packages/*/* 一起构建，同步流程记在 vendor/README.md。你可以不改它，但读它是必要的——不懂 Fiber 就看不懂"卸载为什么干净"。见 /cordis-lifecycle。

误解五："219 个 package 是过度工程。" 换个角度看：21 个 tool-* 包和 32 个 ui-* 包（实测数量）占了近四分之一，它们本质是"一个能力一个包"的直接结果。docs/architecture.md:102 给出的收益是：文件系统和子进程 Provider 共享同一个执行世界，把它们指向远程沙箱，Bash、PTY、LSP 一起搬走，不需要 fork 任何 Provider。分包的代价换来的是这个。【设计记录】

误解六："waterfall 事件里我不调 next() 只是少做一步。" 不是少做一步，是流程断在你这儿。docs/architecture.md:84 说 waterfall 的监听者"must call next() to delegate"。而 serial 的 agent/turn-stopping 根本没有 next()，两者写法不能互抄。【设计记录】

三道自测题 ​

第一题：某人给 Harness 加了一个功能：每次请求前把当前 git 分支名塞进系统提示。他在 agent/pre-step 的监听里读 git branch 然后拼到消息里，没有新增任何 session event。这个实现违反了什么原则？会在什么场景下暴露出问题？

参考答案

违反 docs/architecture.md:96 的 Model-visible means logged：任何进入模型请求的内容都必须能从日志重建，而且有运行时不变量在断言这件事。

暴露场景至少两类。第一，回放/续跑不一致：模型历史是 deriveMessages()（packages/core/session/src/index.ts:726）从日志现算的，日志里没有这段分支名，重启后重建出的上下文就和当时发出去的请求不一样了。第二，不变量直接报错：docs/architecture.md:96 说有运行时断言，packages/core/agent-loop/src/invariant.ts 与 packages/core/session/src/invariant.ts 都存在，packages/core/agent-loop/tests/invariant.spec.ts 专测这类失败。

正确做法：扩展 SessionEventMap 加一种事件，从日志渲染进请求。参照 packages/context/agent-instructions、packages/context/time-context 这几个"往上下文里塞东西"的包是怎么做的。

第二题：你在 tools/execute 上挂了一个插件，想给所有工具加统一超时。同事在 agent/turn-stopping 上挂了一个插件，想在回合收尾时写一份总结。两人都照抄了对方的写法。谁会出问题，为什么？

参考答案

照抄的方向决定谁挂。 docs/architecture.md:84：tools/execute 是 waterfall，监听者必须调 next()；agent/turn-stopping 是 serial，没有 next()。

  • 如果超时插件抄了 serial 写法（不调 next()），tools/execute 的会签链在它这里断掉，后续包装器和真正的派发都不会跑，工具直接不执行。这是硬故障。
  • 如果总结插件抄了 waterfall 写法，去调一个不存在的 next()，会直接抛错；就算被容错吞掉，它也拿不到 waterfall 那种"改写并往下传"的语义，因为 serial 不传值。

深层教训：vendor/cordis/src/events.ts:32 的五种 DispatchMode 决定了监听者的签名契约，挂事件前先确认这个事件是哪种模式，不能凭事件名猜。

第三题：SESSION_FORMAT_VERSION 现在是 0（packages/core/session/src/types.ts:56），SQLite 的 SCHEMA_VERSION 已经是 15（packages/session/session-persistence-sqlite/src/schema.ts:20）。一个已经迭代到 15 的项目，为什么另一个版本号还停在 0？这两个数字各自版本化的是什么？

参考答案

它们版本化的是两个正交的东西，源码注释自己说了。

SCHEMA_VERSION（schema.ts 的注释）版本化的是磁盘表结构，"Bumped only on a breaking change to the table layout; orthogonal to a session's own version"。表结构改一次就 +1，改了 15 次，很正常。

SESSION_FORMAT_VERSION（types.ts 的注释）版本化的是事件词表（"the EVENT vocabulary"），并且按 session 存在 sessions 行里，不是全局的。

停在 0 的原因是显式的策略选择，不是忘了：AGENTS.md:7（Pre-release stance 段）写着后端拒绝旧的磁盘格式，SQLite 用单调递增的 SCHEMA_VERSION，而 dsh-session 把 SESSION_FORMAT_VERSION 保持在 0 且不做任何兼容承诺。发布前没有外部消费者，所以选"正确的地基"而不是兼容垫片。

推论：这两个数字不能互相替代。换持久化后端（SQLite → JSONL）不动事件词表；加一种新 session event 类型才可能需要动 SESSION_FORMAT_VERSION。
