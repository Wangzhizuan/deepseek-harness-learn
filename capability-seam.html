Capability 三件套 ​

这页解决什么问题 ​

仓库里有 219 个 package，你会看到大量成组出现的名字：shell / bash-local / bash-sandbox / tool-bash。第一反应通常是"拆太碎了"。

这页要说明的是：这不是分包风格问题，是一条被写进 AGENTS.md 的硬规则。 AGENTS.md:109 的原话是 A capability seam comprises Service Definition / Service Provider / Consumer roles.（一个能力接缝由服务定义 / 服务提供方 / 消费方三个角色共同构成），同一行还补了一句 It is complete, never one role（接缝是完整的能力，绝不是其中某一个角色）。【设计记录】

这页解决三件事：（一）三个角色各自在源码里长什么样；（二）为什么"换一个 Provider"能做到消费方完全无感；（三）request / spec 拆分这条模板规则到底在防什么。

不在本页范围内：每个接缝的具体协议（ctx.fs、ctx.web、ctx.lsp 等）；工具执行管道的完整拦截点（见 /one-turn）。

先用人话解释 ​

Service Definition 是"插槽规格书"。 它声明一个服务键，并规定这个键上的对象必须有哪些方法。以 shell 为例：packages/shell/shell/src/index.ts:40 用 declare module '@deepseek-ai/cordis' 把 shell: ShellExecutor（:42）挂到 Context 的类型上，:65 的 export abstract class ShellExecutor extends Service { 是那份规格书本身。【源码事实】

Service Provider 是"符合规格的机器"。 它继承那个抽象类、实现所有抽象方法，然后作为插件被挂上去。本机执行的那台是 packages/shell/bash-local/src/index.ts:102 的 export class LocalBashExecutor extends ShellExecutor {。【源码事实】

Consumer 是"用这个能力的岗位"。 它 inject 服务键、按规格书调方法，不知道也不该知道背后是哪台机器。模型能看见的那个 bash 工具是 packages/shell/tool-bash/src/index.ts，:31 的 export const inject = ['tools', 'shell', 'systemPrompt', 'shellEnv'] 就是它的依赖声明。【源码事实】文件第 2 行的注释直接自称 Model-facing Consumer of the ctx.shell capability seam。【源码事实】

规格书为什么必须是抽象类，不能是 TypeScript interface？ 因为它要同时承担运行期职责：ShellExecutor extends Service，而 vendor/cordis/src/service.ts:57 的 self.ctx.reflect.provide(name, self, this[symbols.check]) 说明 Service 的构造过程本身就是"把自己注册到那个键上"。【源码事实】interface 编译后什么都不剩，占不住键。docs/glossary.md:9 明确写着 Service Definition 是 an abstract class such as ShellExecutor, or a concrete registry such as WebRuntime, never a TypeScript interface。【设计记录】

一个键上只能有一个 Provider 在跑。 packages/shell/shell/src/index.ts:48 的注释说得很直接：加载第二个实现会抛错，"which is cordis' standard duplicate-service behavior"。【源码事实】执行点是 vendor/cordis/src/reflect.ts:290。

智能工厂比喻 ​

沿用本站统一映射（完整对照见 /glossary）。

设备插槽 = capability seam（能力接缝）。 插槽是"能装一台什么机器"这件事的整体，不是某台机器。

统一能力接口 = Service Definition。 墙上那块插槽规格书：接口尺寸、电压、必须支持哪几个按钮。

真正提供能力的机器 = Service Provider。 按规格书造出来、插上去的那台。本机执行的一台、沙箱里执行的一台，都能插同一个插槽。

使用能力的岗位 = Consumer。 站在插槽前面按按钮的人。他只认规格书上的按钮，不认机器牌子。

派工单与作业规格分开 = request/spec 拆分。 岗位递上去的是一张派工单（可以留空："超时按默认来"）。机器先把它翻译成一份完全填满的作业规格（超时 30 秒、工作目录 /repo、输出上限 1MB），再照这份规格干活。翻译这一步是公开的、可以单独检查的。

换机器不换岗位。 把本机那台拔下来、换成沙箱那台，插槽和规格书不变，岗位上的人完全感觉不到。

比喻的限制 ​

第一，"插槽"不是一个可以指出来的东西，它是三个包的关系。 比喻里插槽是墙上一个实物。源码里没有任何一个文件叫"seam"。AGENTS.md:109 强调 It is complete, never one role——"接缝"这个词只能用来指三角整体，指某一个角色时必须叫它的角色名（Definition / Provider / Consumer）。【设计记录】说"我改了 shell 这个 seam"是不精确的表述。

第二，"同型号可以摆两台"在这里不成立。 packages/shell/shell/tests/service.spec.ts:78 的用例标题就是 loading a second implementation throws (one bash service per context — cordis standard)，:82 断言错误信息包含 service "shell" has been registered。【测试行为】要在同进程里跑两套，得靠 Cordis 的 isolate 另开 realm，见 /cordis-lifecycle。

第三，"岗位一定直接对着插槽"不对。 一个看起来很像 shell 消费者的包，可能消费的是另一个接缝。packages/shell/tool-bash-persistent/src/index.ts:402 的 export const inject = ['tools', 'terminals'] —— 它在 packages/shell/ 目录下、名字里带 bash，但它 inject 的是 terminals，不是 shell。【源码事实】按目录名或包名猜角色会猜错，唯一可靠的判据是 inject 那一行。

第四，"机器插上就直接干活"漏掉了翻译这一步。 AGENTS.md:111 是一条对所有包边界都成立的规则：defaulting 必须是拥有方实现里一个显式的 resolve(request): Spec 步骤，绝不能是 run() 里藏的 ?? default，并点名 dsh-shell 的 request/spec 拆分是模板。【设计记录】比喻里"机器自己知道默认值"恰好是这条规则要禁止的写法。

第五，"换机器完全无感"有一个例外：消费方可以主动问"我现在挂的是哪种机器"。 packages/shell/tool-bash/src/index.ts:192 读了 ctx.shell.sandboxMode（定义在 packages/shell/shell/src/index.ts:75），用来决定提示词与审批策略。【源码事实】这不是破坏抽象，而是规格书本身暴露的一个查询点——差别在于它问的是"沙箱模式"这个规格化概念，而不是"你是不是 bash-local"。

常见误解 ​

误解一："Service Definition 用 interface 就够了，抽象类太重。" 不够。Definition 要在运行期占住 ctx.<key> 这个键：vendor/cordis/src/service.ts:57 的 provide(name, self, ...) 是构造 Service 时执行的。【源码事实】docs/glossary.md:9 直接把 never a TypeScript interface 写进定义。【设计记录】

误解二："三个角色必须是三个包。" 不必。docs/glossary.md:9 的原话是 Roles normally occupy separate packages when they evolve independently，并举了反例：dsh-llm 自己同时拥有 Definition 和 Consumer。【设计记录】AGENTS.md:109 也说 split only when roles evolve independently。判断标准是"会不会各自独立演进"，不是"要不要好看"。

误解三："看包名/目录就能判断角色。" 会判断错。packages/shell/tool-bash-persistent 在 packages/shell/ 下、名字里有 bash，但 :402 的 inject 是 ['tools', 'terminals']，它不是 ctx.shell 的 Consumer。【源码事实】唯一可靠的判据是 inject 那一行和 extends 那一行。

误解四："默认值写在 run() 里更省事，反正结果一样。" 结果不一样，而且这是被明文禁止的写法。AGENTS.md:111：defaulting 是拥有方实现里一个显式的 resolve(request): Spec 步骤，never a hidden ?? default inside run()。【设计记录】代价很具体：藏在 run() 里的默认值无法被单独断言，也让子类没法覆写默认策略——packages/shell/bash-sandbox/src/index.ts:44 那个子类正是靠覆写 resolve() 来盖上沙箱默认值的。

误解五："换 Provider 需要同时改 Consumer。" 不需要，这正是接缝存在的理由。docs/capability-seams.md:448 那一行的说明写着：sandboxed、remote 或 PowerShell 执行器可以替换 bash-local without touching them（不用碰那些消费方）。【设计记录】源码侧的证据是 packages/shell/tool-bash/src/index.ts 全文只通过 ctx.shell.resolve/run/start 与 ctx.shell.sandboxMode 四个入口访问这个能力（:192、:370、:380）。【源码事实】

误解六："ctx.shell.sandboxMode 这种读法破坏了抽象。" 不破坏。它是 Definition 自己暴露的规格化查询点（packages/shell/shell/src/index.ts:75），返回的是 SandboxMode 这个规格化概念，而不是实现类名。【源码事实】破坏抽象的写法长这样：if (ctx.shell instanceof LocalBashExecutor)。

误解七："工具本体就是能力实现。" 不是。工具本体（packages/shell/tool-bash/src/index.ts:330 的 execute）负责的是面向模型的参数、提示与呈现；真正执行的能力在 Provider 里。两者被 ctx.shell 这条缝隔开，所以同一个能力可以既被模型工具用、也被 hooks 桥（packages/hooks/hooks-codex/src/index.ts:41）用。【源码事实】

三道自测题 ​

第一题：你要新增一个"在远程容器里执行命令"的能力。同事的方案是：在 packages/shell/tool-bash 里加一个 mode: 'remote' 参数，工具体内部 if (mode === 'remote') 走一套新代码。这个方案违反了哪条规则？正确的做法是什么？改动落在哪几个文件？

参考答案

违反 AGENTS.md:109：接缝是完整的三角，角色不能混。 在 Consumer 里塞执行逻辑，等于让"使用能力的岗位"同时变成"提供能力的机器"。【设计记录】后果是：packages/hooks/hooks-claude-code/src/index.ts:42 和 packages/hooks/hooks-codex/src/index.ts:41 这两个同样 inject shell 的消费方拿不到这个新能力，因为它被埋在另一个消费方内部了。【源码事实】

正确做法：新增一个 Provider。 写一个 class RemoteShellExecutor extends ShellExecutor（照 packages/shell/bash-local/src/index.ts:102 的形状），实现 resolve / run / start 三个抽象方法（packages/shell/shell/src/index.ts:85、:93、:100），然后在配置层选它。【源码事实】

改动落点：一个新包 + 一行配置。 packages/shell/tool-bash、packages/shell/shell、packages/hooks/* 一行都不用改——docs/capability-seams.md:448 那一行的说明就是这个承诺：替换执行器 without touching them。【设计记录】

还有一个更省事的可能性值得先确认：如果"远程"本质上是"同样的 bash，只是进程跑在别处"，那么该换的可能是下游的 ctx.subprocess Provider（packages/subprocess/subprocess/src/index.ts:70、:102），连 shell 层都不用动。这一层判断是 seam 分层带来的直接收益。【跨源码分析】

第二题：ShellExecRequest（packages/shell/shell/src/types.ts:38）里 timeoutMs 是可选的，ShellExecSpec（:86）里是必填的。为什么不让 run() 直接接收 request、内部 ?? 30000 完事？请给出两个具体代价，并各指一处源码支持。

参考答案

规则出处是 AGENTS.md:111：defaulting 必须是拥有方实现里显式的 resolve(request): Spec，never a hidden ?? default inside run()，并点名 dsh-shell 的 request/spec 拆分是模板。【设计记录】

代价一：默认值变得不可断言。 现在"默认值是什么、上限怎么 clamp"可以单独测：packages/shell/bash-local/tests/executor.spec.ts:62 的 caps per-call timeouts at maxTimeoutMs 不需要真的跑一条超时命令就能验证；:136 的 resolve() carries stdin/env/dshEnv onto the spec, and run() threads them to the command 把"填规格"和"照规格执行"分成两个可独立断言的阶段。【测试行为】藏进 run() 之后，这两个断言都得靠副作用间接推断。

代价二：子类没法覆写默认策略。 packages/shell/bash-local/src/index.ts:169 的 sandboxPolicy: request.sandboxPolicy, 是原样透传，注释明确说本机执行器从不约束、这个字段在这里是惰性的，沙箱子类通过覆写 resolve() 来盖上自己的默认值；packages/shell/bash-sandbox/src/index.ts:44 的 SandboxBashExecutor extends LocalBashExecutor 就是这个子类。【源码事实】如果默认值散落在 run() 内部的分支里，子类要么复制整个 run()，要么给基类加钩子——两条路都比覆写一个纯函数差。

第三个代价（附赠）：run() 的可读性。 packages/shell/bash-local/src/index.ts:211 的 run(spec) 拿到的是一份完全确定的规格，读它的人不需要回头找"这个值到底哪来的"。

第三题：给你一个陌生包 packages/xyz/foo，你要在三十秒内判断它在某个接缝里扮演什么角色。你会看哪三行？分别看到什么就能得出什么结论？如果三行都不指向同一个键，说明什么？

参考答案

第一行：declare module '@deepseek-ai/cordis' 附近。 有它、并且里面给 interface Context 加了一个键（形如 packages/shell/shell/src/index.ts:40–:42 的 shell: ShellExecutor），说明这个包是 Service Definition：它拥有这个键和它的词表类型。【源码事实】

第二行：export ... class X extends Y。 Y 是某个 Definition 的抽象类（形如 packages/shell/bash-local/src/index.ts:102 的 extends ShellExecutor），说明它是 Service Provider。顺带看紧跟的 static inject（:103 的 ['subprocess']）就知道它自己又消费了哪些下游接缝。【源码事实】

第三行：export const inject = [...]。 里面出现某个服务键（形如 packages/shell/tool-bash/src/index.ts:31），说明它是那个键的 Consumer。【源码事实】

三行不指向同一个键，说明这个包同时扮演多个角色，或者扮演的是别的接缝的角色——这不一定是问题。 docs/glossary.md:9 明确允许一个包持有多个角色，条件是它们属于同一件事（举的例子是 dsh-llm 同时拥有 Definition 和 Consumer）。【设计记录】AGENTS.md:109 的配套判据是 split only when roles evolve independently。【设计记录】

最典型的"看名字会猜错"案例：packages/shell/tool-bash-persistent，目录在 shell/ 下、名字里有 bash，但 :402 的 inject 是 ['tools', 'terminals']——它是 ctx.terminals 的 Consumer，不是 ctx.shell 的。【源码事实】
