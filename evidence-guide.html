证据阅读说明 ​

这页解决什么问题 ​

本站的每条关键结论后面都带着一个证据标签，比如【源码事实】、【设计记录】。这页告诉你每种标签代表什么、可信度有多高、你自己怎么复核，以及本站的锚点校验系统是怎么工作的。

读完这一页，你能独立判断一条结论的可靠性，而不是被动地接受。本站是非官方的中文源码学习材料，不是 DeepSeek Harness 的官方文档；结论以源码为准，证据标签和锚点只是帮你快速定位到源码对应位置的工具。

六种证据标签 ​

每种证据标签对应 check-anchors.ts 中 KINDS 集合的一个值（learn/scripts/check-anchors.ts:40）。标签出现在正文中括号内，如【源码事实】。kind 字段在页面 frontmatter 的 anchors 数组里声明，由 check-anchors.ts 在每次运行时校验。

1. 【源码事实】— kind: source ​

含义：结论直接来自源码文件中的一行或多行代码。是最强证据，因为源码是仓库里唯一不依赖外部解释的权威信息来源。

可信度：最高。只要该文件在 check-anchors 校验时对应的行仍然包含期望内容，结论就是可靠的。如果该行被改过，校验会标记为"漂移"或"失效"。

你自己怎么复核：打开页面底部"本页元信息"区域，找到对应锚点的 path:line 链接，点击即可跳转到 GitHub 上该 commit 的对应行。也可以在你的本地仓库中打开同一文件同一行。

例子：

SESSION_FORMAT_VERSION 当前值为 0（packages/core/session/src/types.ts:56）。【源码事实】

上面这条结论的 frontmatter 锚点声明为：

yaml
- path: packages/core/session/src/types.ts
  line: 56
  expect: "SESSION_FORMAT_VERSION"
  kind: source

2. 【测试行为】— kind: test ​

含义：结论来自测试文件（.spec.ts）中描述的行为。测试文件描述的是"代码应该怎么做"，而不是"代码实际怎么做"——但测试本身就是可执行的行为规范，比文档更可靠。

可信度：高，但低于【源码事实】。测试可能因为 mock 覆盖不全、边界情况遗漏、或测试本身有 bug 而给出不完整的图景。check-anchors 对测试锚点的校验逻辑和【源码事实】完全一致：在目标行里找期望子串。

你自己怎么复核：和【源码事实】一样，点击锚点链接跳转到测试文件对应行，用 pnpm run test 跑一遍确认测试仍然通过。

例子：

session.deriveMessages() 在测试中被直接调用，用于确认从事件到模型消息的投影逻辑（packages/core/session/tests/session.spec.ts:54）。【测试行为】

3. 【运行验证】— kind: runtime ​

含义：结论是实际运行代码后观察到的行为。不是从源码静态推导的，也不是从测试推出来的，而是真的跑了一遍 pnpm dsh --profile headless "..." 或 pnpm run demo:acp 后记录下来的。

可信度：高，但受限于当时运行的版本、配置和环境。如果代码或其依赖更新了，这条结论可能不再成立，但 check-anchors 无法自动检测——因为运行验证锚点指向的仍然是源码中某行，而不是运行时的日志输出。

你自己怎么复核：按本站相同的方式跑一遍命令。大多数运行验证锚点会注明具体命令。

例子：

运行 pnpm dsh --profile headless "echo hello" 后，session log 中第一个 turn/start 事件出现在第 3 条记录位置。【运行验证】

4. 【设计记录】— kind: design ​

含义：结论来自仓库中的设计文档，包括 AGENTS.md、docs/architecture.md、docs/glossary.md、docs/defensive-patterns.md 等。这些文档是项目维护者写的，描述的是"项目应该是什么样"——设计意图，而非实现细节。

可信度：中高。设计文档是项目维护者写的第一手材料，但可能落后于实现。AGENTS.md 作为仓库规范文件，可信度最高；docs/ 下的其他文档次之。check-anchors 对设计文档锚点的校验逻辑和源码一致。

你自己怎么复核：点击锚点链接查看文档原文，再对照源码看实现是否和文档描述一致。如果文档说"插件注册返回 disposer"，但源码中某处没有返回 disposer，文档就是对的而实现有 bug，或者文档过时了。

例子：

一切皆插件（everything is a plugin，AGENTS.md:3）。【设计记录】

5. 【跨源码分析】— kind: cross ​

含义：结论不是从单一文件或单一文档得出的，而是跨多个文件、多个 package 分析后得出的推断。这种推断对理解架构很有价值，但它不是任何一个文件的直接陈述。

可信度：中。跨文件分析的结论依赖分析者的理解，可能有遗漏或误解。check-anchors 对跨源码分析锚点的校验和单文件锚点一致——它只验证每个锚点指向的单个文件行是否仍然包含期望内容，不验证跨文件的关系是否仍然成立。

你自己怎么复核：按锚点逐文件查看，再自己对照着看。如果三条锚点分别指向 agent.ts、session.ts、types.ts，你需要自己理解它们之间的关系，本站只帮你把文件位置和行号标记出来。

例子：

agent-loop 发送 turn/start 事件（packages/core/agent-loop/src/agent.ts:255）后，Session.append 将其写入只追加日志（packages/core/session/src/index.ts:604），事件类型由 SessionEventMap 约束（packages/core/session/src/types.ts:236）。这三处构成了一条完整的"事件发出 → 日志写入 → 类型约束"链路。【跨源码分析】

6. 【未验证判断】— kind: unverified ​

含义：结论是本站作者基于阅读经验做出的判断，但尚未找到精确的源码锚点来证实。这类判断可能对（比如"这个包似乎没有被任何地方 import"），也可能错（因为有的 import 路径不直观）。

可信度：低。在看到反证之前可以当作参考，但不应作为决策依据。check-anchors 对 kind: unverified 做特殊处理：如果 path 和 line 都缺失，直接跳过不校验（learn/scripts/check-anchors.ts:207）；如果提供了 path 和 line，仍然正常校验，但标记为 skipped 而非 stale。

你自己怎么复核：逐条质疑。对于"某包似乎没有被引用"的判断，用 grep 全仓库搜索确认；对于"某设计可能是为了"的判断，直接看源码验证。

例子：

packages/e2b/ 的 sandbox 适配器似乎没有被任何其他 package 直接依赖，它可能是一个独立的 POC 模块。【未验证判断】

锚点校验系统 ​

本站的每条证据标签都对应一个 frontmatter 锚点，由 learn/scripts/check-anchors.ts 脚本在每次运行时校验。

图说明：这就是下面七条规则的流程形态。三个终态需要你行动——格式错误改 frontmatter 的 kind，漂移改行号，失效要回去核对源码是否真的变了。只有"命中"和"跳过"是无需处理的。

校验逻辑 ​

check-anchors.ts 的校验过程（learn/scripts/check-anchors.ts:191）：

  1. 读取每个页面的 frontmatter，提取 anchors 数组。
  2. 对每条锚点，打开它声明的 path 文件，跳到第 line 行，检查该行是否包含 expect 子串（不是精确相等，而是 includes，所以代码格式化不会导致误报）。
  3. 如果该行不包含期望内容，在前后各 5 行（DRIFT_WINDOW = 5，learn/scripts/check-anchors.ts:37）的窗口内搜索同一内容。
  4. 窗口内找到了 → 标记为"行号漂移"，警告但不报错（exit 0）。
  5. 窗口内找不到 → 标记为"锚点失效"，报错退出（exit 1，learn/scripts/check-anchors.ts:322）。
  6. kind: unverified 且无 path/line → 跳过不校验。
  7. kind 不在六种合法值内 → 标记为格式错误，报错退出。

校验结果 ​

校验结果写入 learn/.vitepress/anchor-status.json（learn/.vitepress/config.ts:68 中 LearnMeta 接口的 anchors 字段），包含：

  • checkedAt：校验时间（ISO 格式）
  • commit：校验时仓库所在的 commit
  • total：全站锚点总数
  • staleCount：失效锚点数
  • driftedCount：漂移锚点数
  • pages：按页面路由分组的详细结果

每个页面的 PageStatus 包含 stale（失效）、drifted（漂移）和 invalid（格式错误）三个数组，每个数组元素都是一条 AnchorReport，包含 path、line、expect、kind、reason（失败原因）等信息。

页面底部展示 ​

learn/.vitepress/theme/PageMeta.vue 在每个页面底部渲染锚点校验状态（learn/.vitepress/theme/PageMeta.vue:84）：

  • 失效：红色警告框，列出所有失效锚点，提示"结论可能过期"。
  • 漂移：黄色提示框，列出所有漂移锚点，提示"引用内容仍在，但行号已变化"。
  • 全部命中：绿色文字，无警告框。

页面底部还会显示当前源码 commit、页面生成时间、适用范围（scope 字段），以及本站的免责声明（learn/.vitepress/theme/PageMeta.vue:191）。

证据标签的局限 ​

本站的证据标签和锚点校验系统有几个已知局限，你在阅读时应该心里有数：

  1. 锚点校验只检查单行子串匹配。一条结论说"A 和 B 共同构成 C"，锚点校验只验证 A 那行还在、B 那行还在，不验证它们之间的关系是否仍然成立。这是【跨源码分析】天然的风险。
  2. 锚点校验不检查语义变化。某行代码从 const x = 1 变成 const x = 2，锚点校验不会报错——因为 expect: "const x" 仍然匹配。本站作者在写 expect 时会尽量选择语义关键的标识符（如函数名、常量名），但无法完全消除这种风险。
  3. 未验证判断没有锚点校验。本站的所有【未验证判断】汇总在 /coverage 页面中，你可以逐条复核。
  4. 锚点校验依赖 git 和文件系统。它在提交前运行（pnpm run learn:check），但 VitePress 构建时只是读取上一次的校验结果（learn/.vitepress/anchor-status.json），不会重新跑校验。所以在两次校验之间，如果代码改了但没重新校验，页面底部的状态可能滞后。
  5. VitePress 构建允许死链。config 中设置了 ignoreDeadLinks: true（learn/.vitepress/config.ts:287），因为页面是逐步添加的，一个尚未写好的页面不应导致构建失败。check-anchors 和 check-mermaid 才是真正的质量门。
