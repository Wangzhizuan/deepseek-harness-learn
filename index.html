这页解决什么问题 ​

DeepSeek Harness 有 219 个 package（packages/*/*/package.json 实测数量），分布在 packages/ 下 49 个一级分组目录里，另有 vendor/ 下 9 个上游 workspace 成员、apps/ 下 2 个产品装配。如果你从 package 列表开始读，第一天会全部花在"这个包是干什么的"上，第二天会放弃。

这个站解决的就是这一个问题：给你一条读者跟得住的顺序，让你在 30 分钟内知道这个项目是什么，在半天内理解它为什么这么设计，然后才按需要下潜到具体源码。

先说清定位：本站是非官方的独立中文研究材料，由读源码整理而成，不是 DeepSeek Harness 的官方文档。官方文档在仓库的 docs/ 目录（docs/architecture.md 是架构主文档）。本站每条关键结论都带证据标签和 path:line 锚点，读法见 /evidence-guide。本站作为独立 pnpm workspace 成员存在（pnpm-workspace.yaml:13 的 - learn），只读取仓库作为证据，不参与官方文档流水线。【设计记录】

三条路线 ​

图说明：从本页出发有三条互不冲突的路线。路线一读 /harness-explained 和 /repo-map 两页；路线二在路线一之上依次读 /cordis-lifecycle、/one-turn、/session-log、/capability-seam 四篇核心页；路线三以 /source-order 为总纲，按你的具体目标挑源码文件精读。三条路线是递进的，不是三选一。

路线一：30 分钟认识项目 ​

适合：完全没听说过 Agent Harness、Cordis、插件架构的人。会基本 TypeScript 就够。

顺序页面预计耗时
1/harness-explained20 分钟
2/repo-map10 分钟

读完你能回答：

  • Harness 和"一个调用大模型的脚本"差在哪？为什么它需要 219 个 package？
  • "一切皆插件"（everything is a plugin，AGENTS.md:3）具体是什么意思——哪些东西是插件？【设计记录】
  • turn（回合）和 step（步）的区别是什么？
  • 219 个 package 分成哪十几个可记住的组？我要改一个工具应该去哪个组？
  • vendor/cordis 和 packages/ 的分界线在哪？

路线二：半天理解架构 ​

适合：有前端开发经验，但对进程、事件流、持久化、Service Provider 这些后端/框架概念陌生的人。

顺序页面预计耗时主题
1/harness-explained20 分钟整体图景（路线一已读可跳过）
2/cordis-lifecycle60 分钟插件生命周期：Context、Fiber、可逆副作用
3/one-turn60 分钟一个回合怎么跑完：事件顺序、waterfall 拦截点
4/session-log50 分钟只追加的会话日志：为什么"模型看得见就必须记下来"
5/capability-seam50 分钟能力接缝三角：Definition / Provider / Consumer
6/repo-map15 分钟回头看仓库地图，此时每个分组都有意义了

合计约 4.5 小时，含中间停下来自己 grep 的时间。

读完你能回答：

  • 一个插件被卸载时，它注册过的服务、事件监听、定时器为什么会自动消失？谁负责回收？
  • turn/start（packages/core/agent-loop/src/agent.ts:255）到 turn/end（同文件 :319）之间发生了什么，中间可以插进去哪些拦截点？【源码事实】
  • 为什么 SESSION_FORMAT_VERSION（packages/core/session/src/types.ts:56，当前值 0）和 SQLite 的 SCHEMA_VERSION（packages/session/session-persistence-sqlite/src/schema.ts:20，当前值 15）是两个独立的版本号？【源码事实】
  • 把文件系统 Provider 换成远程沙箱，为什么 Bash、PTY、LSP 会跟着一起搬走？
  • 我想加一个新工具，需要动哪三个角色的代码？能不能只写一个包？

路线三：按目标精读源码 ​

适合：已经读完路线二，现在有具体任务（加工具、换模型、查一个 bug、改持久化）。

顺序页面预计耗时
1/source-order20 分钟选路 + 数小时精读

/source-order 不是又一篇导览，它是一张按目标分岔的源码清单：给出"读了性价比最高的前 10 个 package"的固定顺序，以及六条按任务分岔的精读路径，每条都落到具体文件和行号。

读完你能回答：

  • 我这个任务需要读哪 5 个文件，不需要读哪 200 个包？
  • 怎么用 tests/ 目录里的 640 个 .spec.ts 当文档反查行为？
  • 一个真实调用链从 apps/cli/src/bin.ts 到 SQLite 落盘经过哪些文件？

随时可查的三页 ​

这三页不属于任何路线，是全站的参考层，遇到不认识的词或想核对证据时回来查：

  • /glossary — 术语表。全站术语的唯一权威页，五列对齐：真实术语 / 英文 / 比喻里的说法 / 一句话解释 / 源码锚点。
  • /evidence-guide — 证据阅读说明。六类证据标签（【源码事实】【测试行为】【运行验证】【设计记录】【跨源码分析】【未验证判断】）各自的含义、可信度，以及你自己复核的具体命令。
  • /coverage — 覆盖与未验证判断。本站实际读了哪些目录、绝大多数 package 没读、所有【未验证判断】汇总成表、以及页面过期的判断方式。

一个贯穿全站的比喻 ​

为了让 A 层读者能进门，本站用智能工厂作为统一比喻，全站映射一致（完整对照见 /glossary）：

Harness 是智能工厂，profile 和 bundle 是工厂方案和设备套装，Cordis Context 是厂区公共设施与连接系统，plugin 是可插拔工作站，Fiber 是工作站的一次运行实例，Service Definition 是统一能力接口，Provider 是真正提供能力的机器，Consumer / Tool 是使用能力的岗位，Agent 是任务工长，Agent loop 是任务调度流程，Session log 是只能追加的生产流水账，Session event 是一条生产事实。

比喻只是脚手架。/harness-explained 有一整段专讲这个比喻会在哪里失真，之后全站回到真实术语。
